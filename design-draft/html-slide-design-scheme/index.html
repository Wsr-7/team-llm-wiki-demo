团队知识库设计方案

基于 Git Repo 管理、可被 AI 使用、可通过 PR 治理的团队知识工程机制

今天这次分享的主题是团队知识库设计方案。这里说的知识库，不是传统意义上的文档站，也不是单纯做一个 RAG 问答系统，而是一套能把团队知识持续沉淀、可审查、可追溯、还能被 AI 使用起来的工程机制。

我今天主要讲四件事：为什么我们需要它，它参考了什么方法论，为什么总体设计会落到 Git Repo 这条路线，以及第一阶段到底能落什么、后续怎么演进。

这里提前说明一下，大家现在看到的是给团队看的观众视图。我自己的 notes 只用于帮助我讲，不会出现在正式页面里。这也是这次 deck 的一个设计原则：展示内容和讲稿彻底分离。

大家可以带着两个问题来听。第一个问题是，这套方案到底是不是在解决我们真实存在的问题；第二个问题是，如果现在就开始做，第一阶段能不能用很小的投入跑出价值。后面每一部分其实都是在回答这两个问题。

// section 01 · why

现状问题：知识在增长，
但组织记忆没有被工程化

当前常见状态

  • 信息散落在聊天、Confluence、个人笔记、PR、事故复盘里
  • 知道答案的人有限，换岗或离职后责任链容易断
  • 新同学 onboarding 成本高，跨团队协作要反复问人
  • AI 可以总结内容，但不能天然成为事实源

目标状态

  • 正式知识有统一权威层和可审计入口
  • 每条知识都有来源、owner、状态、可信度
  • 团队成员能查，AI agent 也能查
  • 自动化逐步增加，但不绕过人工判断
核心不是“再做一个文档站”，而是把知识沉淀过程本身做成可治理的工程流程。

这一页要先把建设动因讲清楚。我们的问题不是没有内容，而是内容没有形成一个稳定的、可追溯的组织记忆层。大家平时其实都在产出知识，只是这些知识散落在不同地方，而且缺少统一的结构和治理入口。

右边这栏就是我们想要的状态：正式知识必须有来源、有 owner、有状态，既能给人查，也能给 AI agent 查，但前提是不能牺牲可靠性。所以自动化是辅助，人类判断始终是硬门禁。

这里的过渡点很重要。我们不是因为“想上 AI”才做知识库，而是先承认团队知识本来就在流动、在损耗、在重复劳动。AI 只是帮助我们把维护成本降下来，让这套机制真正有可能长期跑下去。

// section 02 · reference

LLM Wiki / LLM Wiki v2 / 内部落地方案

LLM Wiki

核心启发

  • raw sources → compiled wiki，而不是临时拼接问答
  • 强调 schema 和 prompt 是知识编译协议
  • 强调好答案应回填，知识会持续沉淀

三阶段循环

  • Capture / Understand
  • Compile / Curate
  • Query / Feed Back

三层架构与核心操作

  • 三层：Raw Sources / Wiki / Schema
  • 三操作：Ingest / Query / Lint
  • index + log 作为导航与时间线辅助

LLM Wiki v2

增强方向

  • lifecycle / confidence / relation
  • 检索增强、治理增强、自动化增强
  • 更完整的长期运营与质量视角

对我们的意义

  • 让知识不仅可写，还能被持续治理
  • 让 query、review、stale、supersession 串成体系

内部落地方案

企业化调整

  • Git Repo 作为正式权威层
  • PR review 是硬门禁
  • staff-id 作为责任主键
  • 按 Phase 渐进落地，而不是一步到位平台化

我们的取舍

  • 先人工闭环，再自动化
  • 先 formal wiki，再 search / graph / MCP 扩展

这一页我会按你要求拆成三大块来讲。左边先讲 LLM Wiki 的基础思想：知识不是临时问出来的，而是先经过 raw sources，再编译成正式 wiki，并且 query 的结果还要能回填。中间讲 v2 的增强点，它把 lifecycle、confidence、relation、治理这些长期问题补全了。

右边再落到我们的内部落地方案。这里要强调：我们不是照抄，而是在方法论上做企业化取舍，尤其是 Git Repo 权威层、PR 硬门禁、staff-id 责任主键、按 phase 渐进落地这四点。

// section 03 · core decision

核心判断：Git Repo 是权威层，
LLM 是知识编译器

①
Repo 负责什么

正式知识存储、PR 审核、CODEOWNERS、历史、回滚、审计。

②
正式知识怎么进入

只能通过 candidate → patch → PR → review → merge 的链路进入主干。

③
为什么不是文档站

文档站适合阅读入口，但不适合作为正式事实源和审计层。

④
LLM 负责什么

摘要、改写、交叉链接、proposal、query、lint、回填建议。

⑤
LLM 不负责什么

不能无人审阅直接覆盖 active 页面，也不能决定组织规范。

⑥
为什么这点重要

后续的 confidence、CI、lifecycle 都建立在这条边界之上。

一句话：LLM 帮我们降低维护成本，但不取代事实权威和人工判断。

这是全场最重要的一页。一定要把这个判断讲透。为什么是 Git Repo？因为它天然具备我们要的东西：版本历史、PR、review、审计、回滚、权限控制。这些都不是后面补一个搜索层就能替代的。

同时也要把 LLM 的边界讲清楚。它很适合做 compiler，适合从 raw material 提炼知识、整理成候选、生成 patch、辅助 query 和 lint，但它不应该自己成为 authority。这样后面大家再看 confidence、review、Phase 2 CI，就会觉得逻辑是一致的。

// section 04 · repo layout

为什么用 Git Repo：目录结构和关键边界

来源层

raw/
confluence-mirror/
personal/<staff-id>/raw

候选与正式层

inbox/candidates/
wiki/
personal/<staff-id>/wiki

规则与派生层

AGENTS.md
schemas/ templates/ prompts/
indexes/ logs/ graph/

关键文件

  • `AGENTS.md`：agent 协议入口
  • `INDEX.md`：人和 agent 的首要导航入口
  • `source manifest`：让 raw source 可追溯
  • `compile-wiki`：生成 Wiki Proposal
  • `prepare-wiki-patch`：准备正式 PR patch

关键边界

  • `raw/` 只追加，不改原始内容
  • `personal/` 不等于团队共识
  • `mirror/` 与正式 wiki 物理隔离
  • `wiki/` 只能经 PR 进入
  • `indexes/graph/exports` 都是派生产物

这一页不要念目录，要按层解释。第一列是来源层，负责接收原始材料；第二列是候选和正式层，负责知识的编译和定稿；第三列是规则与派生层，负责告诉人和 agent 应该怎么工作，以及怎么生成导航、日志、图关系这些衍生物。

这里最容易被误解的是 personal 和 mirror。personal 是个人知识空间，不代表团队共识；mirror 是外部内容快照，不代表正式知识。只有 wiki 才是正式团队知识，而且必须经过 PR 流程。

// section 05 · workflow

从 raw 到正式 Wiki

Input

Raw / Personal / Mirror

来源进入 raw、personal 或 confluence-mirror

→
Ingest

Source Analysis

ingest-source 先抽取摘要、事实、实体、概念、证据、来源内关系、矛盾、缺口、owner candidates、suggested target pages

→
Compile

Generation

compile-wiki 生成 page frontmatter、wiki candidates、[[wikilink]]、source_refs、related、confidence rationale、review checklist

↓
Use

Wiki / Query / Lint

正式知识开始支持 query、lint、related、后续高价值答案回填

←
Govern

Prepare Patch

准备正式 PR patch，并同步 index / log 草稿

←
Review

PR + Owner Review

review 与 checks 共同决定能否进入正式 wiki，并把结论带回使用闭环

这是给 section 05 的候选页，重点是把整个闭环更明确地画成流程图，而不是按步骤卡片去讲。它更适合现场快速扫一遍，让大家直接看到从输入来源到正式 wiki，再到 query 和 lint 的完整闭环。

讲的时候建议按顺时针顺序走。先从 Input 开始，说明来源可以来自 raw、personal、mirror；然后进入 Ingest 的 Source Analysis，强调这里先做理解，不直接写正式知识；再进入 Compile 的 Generation，把理解编译成候选知识结构。

往下走到 Review 时，强调这是正式门禁；再到 Prepare Patch，说明它负责把成熟候选整理成 PR 可审阅形态；最后落到 Use，也就是正式 wiki 开始支持 query、lint、related 和后续回填。这样一圈下来，大家能更直观看到“知识是怎么被做成产品能力”的。

CODEOWNERS

Jenkins / GitHub Actions

执行 schema、links、source_refs、mirror isolation 等 checks

PR Review

在人类 review 里确认事实、边界、可信度与可执行性

编译流程

  • raw → Source Understanding → Wiki Proposal
  • prepare patch → PR → merge → wiki
  • 一次 source 可能更新多页正式知识

查询流程

  • 先读 INDEX，再检索 wiki
  • 引用 source_refs，输出 related pages
  • 高价值答案可回填为新候选知识

设计原则

  • 来源层只负责接收，不直接晋升为正式知识
  • 治理层是硬门禁，不是装饰性流程
  • 派生层全部可重建，不与权威层混淆

关键收益

  • 人和 AI 都能在同一套知识资产上协作
  • 正式知识可审查、可引用、可回滚
  • 后续 search / MCP / graph 都有稳定基座

// section 07 · boundary

Phase 0 vs Phase 1：先做实，再扩展

Phase 0

  • 创建 repo skeleton
  • 定义 Schema Pack
  • 建立 staff-id 责任映射
  • 准备最小 demo corpus
  • 不要求搜索平台、站点、向量数据库先到位
  • 目标：让人和 agent 都知道怎么协作

Phase 1

  • 跑 ingest / compile / patch / PR 人工闭环
  • 形成第一批正式 wiki 页面
  • 支持基础 query、lint、related pages
  • 演示 personal promotion 与 mirror sample
  • 让团队先看到“真的能用”的价值
  • 目标：先证明这套机制真的有价值
此时先不做：重型平台、图数据库、默认全量同步、无人审阅自动化。

这页是为了控预期。大家一看到“知识库 + AI + 图谱 + 检索”，很容易脑补成一个很大的平台项目。这里要明确，我们第一阶段并不是做全，而是做对。Phase 0 解决的是结构和规则，Phase 1 解决的是闭环和价值验证。

后面那些看起来很高级的能力，例如大规模自动化、图数据库、全量同步，都不是现在先做的重点。只有前面的闭环真的跑通、有价值，后面的增强才值得投入。

// section 08 · roadmap

后续路线：能力逐步增强

Phase 2

  • 质量门禁与 PR 检查
  • CI 中立设计：Jenkins 或 GitHub Actions 二选一
  • schema / links / source_refs / staff-id / visibility checks
  • mirror isolation 与 issue 反馈入口开始标准化

Phase 3

  • 检索与问答增强
  • QMD / rg fallback / 查询评估集 / search corpus
  • 先稳定 cited answers，再逐步引入 embedding
  • 支持 lexical + vector hybrid search 与 query 回填

Phase 4

  • 轻量图遍历与生命周期治理
  • backlinks / wikilink / shared source_refs 导出 sidecar
  • stale / supersession / review SLA / confidence decay

Phase 5

  • 自动化与企业集成
  • Confluence / Jira / Slack / GitHub 的显式 scope ingest
  • agent 自动 PR、MCP / API gateway、AI-ready exports
  • 自动化只开 PR，不绕过 owner review

最后用一页把后续演进收住。这里不要讲太细，只需要让大家知道后面每个 phase 分别解决什么问题。Phase 2 解决质量门禁，Phase 3 解决检索增强，Phase 4 解决关系导航和生命周期治理，Phase 5 开始做企业集成和自动化。

如果要更具体一点去讲，可以这样理解：Phase 2 先让“写进去的东西更可靠”，Phase 3 再让“查出来的东西更好用”，Phase 4 解决“知识之间怎么形成结构和治理”，Phase 5 才开始把外部系统和自动化能力接进来。这个顺序本身就是一种风险控制。

重点不是把能力一次性堆满，而是在同一套权威层上逐步增强，让团队始终能解释每一步为什么值得做，也能在任何一个阶段停下来仍然保持系统可用。
