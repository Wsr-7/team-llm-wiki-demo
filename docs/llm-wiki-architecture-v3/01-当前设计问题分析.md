# 01 — 当前设计问题分析

> 分析对象: `design-draft-v1/`（7 个文件，约 4600 行）、`docs/llm-wiki-architecture-v2/`（9 个文件，约 2900 行）、当前 repo 骨架。
> 结论先行: 方向正确，机制过剩。问题不是"设计得不好"，而是"设计得太多、太早"。

## 1. 总体判断

v1/v2 有三个判断是完全正确的，v3 全部继承：

1. **Git repo 是权威层**，正式知识只通过 PR 进入 `wiki/`。
2. **LLM 是 compiler/maintainer，不是真理来源**——AI 产出必须经人审。
3. **知识要有出处**——正式页面要能回答"这条结论从哪来"。

当前的硬事实（注：`wiki/` 为空是设计阶段的正常状态，占位文件不构成批评依据；真正的问题是下面这个比例）：

```text
设计文档:  约 9300 行（v1 + v2）
校验脚本:  已有 6 个，v2 规划再加约 18 个
知识存放区: 5 个（raw/ inbox/ personal/ confluence-mirror/ wiki/）
Phase 数:  8 个（0, 0.5, 1–6）
真实使用反馈: 0 次（尚无一条知识走完过完整流程）
```

问题不在"还没有内容"，而在**全部机制都设计于任何真实使用反馈之前**——每一个 schema 字段、每一条流转规则都在回答一个尚未被观察到的问题。用户自述的"过度设计、难以落地、不知道从哪开始、学习曲线陡峭"，根源在此。

## 2. 十个结构性问题

### P1. 治理先行病：为第 2000 页设计，卡死在第 0 页

v2 自己的 review 文档（`review/01`，第 6 节）写得很清楚：

- 0–100 页规模只需要 INDEX + CI + PR review；
- claim 级溯源、混合检索、图谱是 500–2000+ 页的能力。

但 v2 的 redesign 仍然把 claim_refs（含 quote_hash、start_line/end_line）、confidence 规则机、memory_tier、检索评测集、图谱 sidecar 全部写进了 schema 和 Phase 计划。**诊断对了，药方开反了。** 团队现在处于第 0 页，所有这些机制的唯一效果是抬高第 1 页的门槛。

### P2. 贡献成本远高于替代品（问人/Confluence）

按 v2 设计，贡献一条"生产问题解决方案"的完整路径是：

```text
建 raw/<category>/<date>-<slug>/ 目录
→ 写 manifest.md（9 个字段，含 source.md 的真实 sha256）
→ 写 source.md
→ 用 ingest prompt 生成 candidate（6 个必备 section + 3 个状态字段 + 4 维质量分）
→ 用 compile prompt 生成 Wiki Proposal
→ 用 prepare-wiki-patch prompt 生成正式页（12+ frontmatter 字段，高危内容加 claim_refs）
→ PR + owner review
```

而替代品是：在 Teams 里 @ 一个人，30 秒得到答案。知识库的竞争对手不是"更差的知识库"，是"问人"。**任何一步捕获成本超过约 5 分钟，普通成员就永远不会走这条路**，系统只剩设计者一个用户。外部调研（见 04 文档）反复验证：内部 wiki 死于维护/贡献负担与所有权缺失，从不死于 schema 不够严谨。

### P3. 候选层重复建设了 GitHub 已有的东西

`inbox/candidates/` 的整套机制——candidate_status 状态机（proposed → in_review → promoted/rejected/superseded）、Review Notes、Decision Log、review 队列目录——与 GitHub PR 的能力一一对应：

| v1/v2 自建机制 | GitHub 原生等价物 |
| --- | --- |
| candidate_status: proposed | Draft PR |
| candidate_status: in_review | PR open + review requested |
| promoted / rejected | merged / closed |
| Review Notes | PR review comments |
| Decision Log | PR discussion + merge commit |
| inbox/reviews/ 各队列 | PR label / GitHub Issues |
| logs/operations.md 审计 | git log / PR history |

自建一套平行状态机意味着：双份维护、双份漂移、双份学习成本。**候选就是 PR，审核记录就是 PR 评论，审计日志就是 git log。**

### P4. 证据链过重，且引入合规风险

v1/v2 要求所有来源全文落盘到 `raw/`（immutable + sha256 + 不许改写）。对团队场景这是三重错误：

1. **成本**：为每条知识建目录、抄全文、算哈希，是 P2 贡献成本的主要构成。
2. **合规**：把 Confluence 页面、Teams 聊天、事故记录**全文复制**进另一个 repo，在外企环境下是数据治理红旗（权限边界被绕过、PII 扩散、保留策略失控）。引用比复制安全。
3. **价值错配**：团队知识的"证据"天然是**可链接的系统记录**——Jira ticket、Confluence 页、incident 频道、监控面板。一个 URL + 日期给出的可核查性，覆盖 95% 的场景；sha256 + 行号锚点 + quote_hash 服务的是"来源会被篡改且无处核查"的威胁模型，团队内部不存在这个威胁。

### P5. 伪精度：confidence 浮点数与四维质量分

`confidence: 0.00–1.00`（外加"disputed 不得高于 0.60"这类规则）和 candidate 的 structure/citation/consistency/actionability 四维评分，都是**没有测量过程的数字**。两个人（或两次 LLM 调用）对同一页面给出的分数不会一致，数字既不能比较也不能聚合，只产生"看起来严谨"的错觉和无穷的校验规则。人类团队对知识可信度的真实表达只有三档：**这是现行做法 / 这个待确认 / 这个已过时**。三个枚举值够了。

### P6. 五个知识存放区 = 每次贡献都要考一次分类学

raw / inbox/candidates / personal/*/raw / personal/*/wiki / confluence-mirror / wiki，外加 logs、indexes、graph、okf。贡献者每次都要先回答"这条东西属于哪个区、什么状态、走哪条流转路径"。**每一条边界都是一笔认知税。** 而实际需要的信任级别只有两级：没审过的（inbox）和审过的（wiki）。

### P7. personal/ 空间是伪需求

个人知识空间放在团队 repo 里，两头不讨好：个人不愿把未成形笔记提交到团队可见的地方（隐私与形象成本），团队又明确规定它"不是团队真理"（那放进来干什么）。个人知识库应该是每个人自己的 llm-wiki（Karpathy 原始模式恰恰是个人模式），**团队 repo 只需要一张"谁负责什么"的路由表**。个人经验想沉淀为团队知识时，路径就是发一个 PR——和其它知识没有任何区别。

### P8. confluence-mirror 方向搞反了

v1/v2 设计的是 Confluence → repo 单向镜像。这会制造一个必然过期的副本，且和 P4 一样有全文复制的合规问题。真实需求是两个：

1. **引用**：wiki 页面需要指向 Confluence 的某页 → 一个链接就够。
2. **搬运**：某 Confluence 页被 agent/人反复需要 → 把**那一页**改写成 wiki 页面（带来源链接），此后 wiki 版本是权威。

而真正有价值的镜像方向是反的：**repo → Confluence 单向发布**（成熟工具现成：kovetskiy/mark、GitHub Actions marketplace 多个），让不碰 git 的同事（PM、QA、新人）在熟悉的 Confluence 里看到 wiki 内容，解决的是采纳问题，不是权威问题。

### P9. 检索与图谱基建缺乏需求证据，且有反证

Karpathy gist 评论区有人做了受控 A/B 实测（archcheck 项目）：28 个每条 claim 都带 `file:line` 引用的高质量 wiki 页面，对比"让 agent 直接 grep 代码库"——**4 个问题正确率打平，token 节省接近零**。结论不是"wiki 无用"，而是：(a) agent 的 grep 能力已经是一个够强的检索引擎；(b) wiki 的价值在于**装那些 grep 不到的东西**（事故结论、决策原因、口头传承），而不是在检索机制上内卷。corpus.jsonl、chunks、RRF 混合检索、图谱 sidecar 在几百页规模内都无法证明自己比 `INDEX.md + rg` 更好——而 v2 连评测集（QUERY_EVAL）都规划了，却没有页面可以被检索。

### P10. OKF 是别人的问题的解

OKF 的设计目标写在其 spec 第 1 节：跨组织、跨系统的知识**交换**格式。团队现状：单团队、单 repo、零外部消费者。OKF 唯一有价值的部分——"markdown + YAML frontmatter + index.md 渐进披露"——v3 本来就是这么做的（这是共同祖先，不是 OKF 的发明）。专门的 export profile、x-team-* 字段映射、conformance 校验，在出现第二个消费方之前是纯负债。**兼容 OKF 的最好方式是保持简单到"天然接近兼容"，而不是建一条导出流水线。**

## 3. 逐特性裁决表

回答用户的直接疑问："llm-wiki v1/v2 的特性都充分发挥了吗？OKF 真的需要吗？"

### 3.1 Karpathy llm-wiki（原始模式）

| 特性 | v3 裁决 | 理由 |
| --- | --- | --- |
| 编译而非检索（wiki 是持久复利工件） | **采用**（核心） | 这是整个项目的立足点 |
| 三层架构 raw/wiki/schema | **改造采用** | schema 层保留（AGENTS.md）；raw 层降级为"来源链接"，不落全文 |
| ingest / query / lint 三操作 | **采用** | 收敛为 3 个 prompt，对应 v3 的捕获/查询/园艺 |
| index.md 目录导航 | **采用** | 实证有效到 100–200 页 |
| log.md 流水 | **放弃** | git log 就是流水；重复记账 |
| 人管方向、LLM 管记账 | **采用** | 团队版的"人"多了一个 reviewer 角色 |
| Obsidian/Marp/Dataview 等 | **不管** | 个人工具偏好，与团队架构无关 |

### 3.2 llm-wiki-v2（agentmemory 扩展版）

注意这篇文档的性质：它是 agentmemory 产品作者写的经验推广文，其特性列表是**产品功能清单，不是需求清单**。

| 特性 | v3 裁决 | 理由 |
| --- | --- | --- |
| 知识有生命周期（stale/supersede） | **简化采用** | 用 `status: needs-review / superseded` 两个枚举 + 园艺例会，不用状态机 |
| confidence 浮点评分 + 衰减曲线 | **放弃** | P5 伪精度；Ebbinghaus 衰减是记忆引擎的机制，不是团队 wiki 的需求 |
| memory 四层分级（working/episodic/semantic/procedural） | **放弃** | 认知科学隐喻，映射到团队场景只剩 inbox/wiki 两级 |
| 实体抽取 + typed 关系图谱 | **推迟**（触发器见 03） | P9；几百页内 wikilink + grep 足够 |
| 混合检索（BM25+向量+图+RRF） | **推迟**（触发器见 03） | P9；先用 INDEX + grep，测到不够再说 |
| 事件驱动自动化 hooks | **推迟** | 先手工闭环跑 3 个月；自动化的对象必须是已验证的手工流程 |
| 质量评分 + self-healing | **放弃/简化** | 评分见 P5；self-healing 的合理部分 = 园艺例会里 agent 出报告 |
| 多 agent mesh sync | **放弃** | git 就是多 agent 的合并协议 |
| 私有/共享分域 | **放弃** | P7，个人空间移出团队 repo |
| 敏感信息过滤 | **采用**（廉价版） | GitHub push protection / gitleaks 一行配置，不自研 check-secrets |
| 审计追踪 | **放弃** | git log + PR 历史就是审计 |
| Crystallization（会话结晶） | **采用**（改造） | 就是"把有价值的问答用 PR 存回 wiki"，不需要专门机制，写进 query prompt 的最后一步 |
| "schema 是真正的产品" | **采用**（核心） | v3 把主要精力放在一份手写的、≤150 行的 AGENTS.md 上 |

### 3.3 OKF

| 特性 | v3 裁决 | 理由 |
| --- | --- | --- |
| markdown + frontmatter + 目录树 | **天然满足** | 共同祖先模式 |
| `type` 必填字段 | **天然满足** | v3 用目录即类型（`wiki/runbooks/` 下就是 runbook），另有 frontmatter 可加 |
| index.md 渐进披露 | **天然满足** | v3 的 INDEX.md 结构与 OKF §6 兼容 |
| 宽容消费（容忍断链/未知字段） | **理念采用** | v3 的校验也只对少数硬规则 fail |
| export profile / x-team-* 映射 / conformance 工具链 | **放弃** | P10；出现第二个消费组织时再花一天写导出脚本即可 |

**直接回答：OKF 不需要。** 保持 v3 的极简结构，未来若需交换，导出是一天的工作量；现在建导出层，是为不存在的消费者付月租。

## 4. v1/v2 中值得保留的资产

推翻的是机制堆叠，不是全部工作。以下资产直接进入 v3：

1. **权威模型**：Git + PR + CODEOWNERS + branch protection（v2 review 中关于 CI/branch protection 未启用的整改意见依然成立）。
2. **staff-id 身份规则**：如果这是公司合规约束则保留，但简化承载方式（见 02 §8）。
3. **prompt registry 思想**：保留，从 6+ 个收敛到 3 个。
4. **模板思想**：保留 runbook / troubleshooting / decision 三个模板（v1 的页面正文结构设计是好的，裁剪后用）。
5. **lint/园艺思想**：保留，从"20 个 CI 脚本"改为"1 个 CI 脚本 + 每双周 30 分钟人机例会"。
6. **query 规则**：v2 的"先读 INDEX、读全文再回答、必须引用、答不出返回 unknown、标记过期页"五条全部保留——这是全套设计里最精华的 agent 行为约束。
7. **v2 review 文档的自我诊断**（review/01 §6 规模-能力对照表）：v3 的触发器体系就是把这张表变成升级开关。
