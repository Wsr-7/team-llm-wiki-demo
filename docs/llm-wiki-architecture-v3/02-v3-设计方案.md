# 02 — v3 设计方案

> 一句话定位: 一个 git repo 管理的、人和 agent 都能直接读写的团队知识库。
> 不绑定入口（Copilot / Claude Code / opencode / 内部 API 模型均可消费），
> 通过 PR 审核积累正式知识，通过双周园艺例会保持健康。

## 1. 设计目标（从痛点出发，不从概念出发）

团队痛点原文拆解为四个可验证的目标：

| 痛点 | v3 目标 | 验收方式 |
| --- | --- | --- |
| 生产问题解决方案 / troubleshooting / runbook 散落各处 | 事故类知识 5 分钟内可捕获进 inbox，双周内进 wiki | 数 `wiki/troubleshooting/` 页面增量 |
| 检索只能问人或搜 Confluence | 人和 agent 都能在 wiki 内自助得到带引用的答案 | 每月统计"wiki 答出的问题数 / unknown 数" |
| 个人经验无处沉淀 | 沉淀路径 = 发 PR，与其它知识无差别 | 数非发起人的贡献者人数 |
| AI Agent 拿不到团队上下文 | 任意 agent 打开 repo 即知道怎么用（AGENTS.md 标准） | 用 Copilot/Claude Code 各答 5 个真实问题做冒烟测试 |

## 2. 七条设计原则

1. **贡献成本 < 问人成本。** 捕获一条知识 ≤ 5 分钟，否则机制设计失败。
2. **两级信任，位置即状态。** `inbox/` = 未审但有用；`wiki/` = 已审团队知识。没有第三级。
3. **GitHub 原生能力优先。** 候选 = PR；审核记录 = PR 评论；审计 = git log；review 队列 = Issues/labels；密钥扫描 = push protection。不自建平行系统。
4. **溯源用链接，不用哈希。** `sources:` 里放 Jira/Confluence/incident URL。可点击核查即为足够的证据强度。
5. **agent 的检索引擎是 grep + INDEX。** 在测量证明不够之前，不建任何检索基建。
6. **schema 是产品，且必须手写、极简。** 有研究表明 LLM 生成的冗长 AGENTS.md 反而降低 agent 任务成功率（见 04）。AGENTS.md 控制在 150 行内，只写"agent 猜不到的团队特有约定"。
7. **升级靠触发器，不靠日历。** 每个后续能力（检索、发布、图谱）绑定一个可观测的疼痛信号，信号不出现就永远不建。

## 3. 总体架构

```text
                     贡献路径                              消费路径
 ┌────────────────────────────────────────┐   ┌────────────────────────────────┐
 │                                        │   │  人: GitHub 网页 / IDE 直接读   │
 │  事故复盘/排障记录/决策/经验             │   │                                │
 │        │                               │   │  agent 入口(任选):              │
 │        ▼  ≤5分钟, 直接 commit main      │   │   - Copilot: Space +           │
 │   inbox/  (未审快速捕获区)              │   │     copilot-instructions.md    │
 │        │                               │   │   - Claude Code: CLAUDE.md     │
 │        │  双周园艺例会:                 │   │   - opencode等: AGENTS.md      │
 │        │  agent 起草→人审→PR            │   │   - 内部API模型: query prompt   │
 │        ▼                               │   │        │                       │
 │   Pull Request  ←──── 个人/agent       │   │        ▼                       │
 │   (候选层=PR本身)      直接发起PR       │   │  读 INDEX.md → grep/读全文      │
 │        │                               │   │  → 带引用回答 / unknown         │
 │        ▼  CODEOWNERS 审核合并           │   │        │                       │
 │   wiki/  (正式团队知识)                 │◄──┼────────┘ 有沉淀价值的回答       │
 │        │                               │   │          回填为 PR              │
 └────────┼───────────────────────────────┘   └────────────────────────────────┘
          ▼ (Phase 3, 触发后)
    Confluence 单向发布 (repo → Confluence, 给不用 git 的同事)
```

要点：**只有一条主流水线**（inbox → PR → wiki），且其中两级（PR、审核）是 GitHub 白送的。agent 和人共用同一条线。

## 4. 目录结构

```text
team-llm-wiki/
├── README.md                    # 人类入口: 这是什么/怎么查/怎么贡献, 1 页说完
├── AGENTS.md                    # agent 入口: 唯一的 schema 文件, ≤150 行, 手写
├── CLAUDE.md                    # 一行文件: "Read AGENTS.md."
├── INDEX.md                     # 全库目录: 每页一行(路径+一句话), 脚本生成
├── .github/
│   ├── copilot-instructions.md  # 一行文件: 指向 AGENTS.md
│   ├── CODEOWNERS               # wiki/** 按域指到真实 GitHub team
│   ├── PULL_REQUEST_TEMPLATE.md # 三个问题: 改了什么/来源是什么/谁该审
│   └── workflows/check.yml      # npm run check, PR 必过
├── wiki/                        # 正式团队知识 (只经 PR 进入)
│   ├── troubleshooting/         # 生产问题: 现象→根因→解法 (痛点第一位, 单列)
│   ├── runbooks/                # 操作手册: 前置→步骤→验证→回滚
│   ├── systems/                 # 系统页: 是什么/边界/依赖/负责人/坑
│   ├── decisions/               # 决策记录: 背景→选项→结论→后果 (轻量 ADR)
│   ├── concepts/                # 领域概念与背景知识 (痛点中的"团队通用知识")
│   ├── guides/                  # how-to 与团队实践
│   └── glossary.md              # 术语表: 单文件, 不是目录
├── inbox/                       # 快速捕获区: 一条知识一个 md, 零门槛, 允许直接 commit
├── team/
│   └── people.md                # staff-id ↔ GitHub ↔ 负责域 路由表 (见 §8)
├── schemas/                     # 文档化 schema: 完整字段规则与示例, AGENTS.md 引用之
│   ├── README.md                # 目录定位与 schema 三形态说明
│   ├── frontmatter.md           # wiki 页面 schema + 目录分类法 + sources 约定
│   └── person.md                # people.md 条目 schema
├── prompts/
│   ├── capture.md               # 原始材料 → inbox 条目/正式页草稿 (含证据摘录规则)
│   ├── query.md                 # 查询协议, 自包含 (可直接作内部 API 模型 system prompt)
│   └── gardening.md             # 园艺协议 (inbox 清理 + 健康检查 + 起草 PR + 三度量)
├── templates/                   # 全类型覆盖
│   ├── troubleshooting.md / runbook.md / system.md
│   ├── decision.md / concept.md / guide.md
│   └── superseded-example.md    # 展示如何正确地废弃一页
├── scripts/
│   ├── lib.ts                   # 共享工具 (扁平 YAML 子集解析, 带嵌套防御)
│   ├── check.ts                 # 可执行 schema: 必填/枚举/链接/owner 存在/INDEX 新鲜度
│   └── build-index.ts           # 生成 INDEX.md
└── docs/                        # 架构文档与历史归档 (不参与知识校验)
```

Schema 的三形态（各司其职，不是重复建设）：**`schemas/` 是文档形态**（人和 agent 阅读的完整规则、分类法与示例），**`scripts/check.ts` 是可执行形态**（机器强制的子集），**AGENTS.md 只引用不复制**。

与 v2 相比删除的顶层目录：`raw/`、`personal/`、`confluence-mirror/`、`logs/`、`graph/`、`okf/`、`indexes/`（降为根级单文件 INDEX.md）、`inbox/candidates|reviews`（inbox 扁平化）。迁移映射见 03 §Phase 0。

## 5. 最小 Schema

### 5.1 wiki/ 页面 frontmatter

```yaml
---
owner: staff:12345678        # 必填: 谁对这页负责
updated: 2026-07-07          # 必填: 最后一次实质确认/修改日期
sources:                     # 强烈建议 (troubleshooting/runbook/decision 必填):
  - https://jira.company.com/browse/PAY-1234
  - https://confluence.company.com/pages/123456
status: needs-review         # 可选: 缺省即"现行有效"; 仅两个非默认值:
superseded_by: wiki/runbooks/payment-failover-v2.md   # status: superseded 时必填
tags: [payment, oncall]      # 可选
---
```

硬规则全部由 `scripts/check.ts` 一个脚本校验（完整字段文档见 `schemas/frontmatter.md`）：

1. `owner`、`updated` 必填；owner 必须是 `staff:########` 格式且存在于 `team/people.md`。
2. `wiki/troubleshooting|runbooks|decisions/` 下 `sources` 非空（链接或 ticket 号皆可）。
3. `status` 若出现只允许 `needs-review | superseded`；`superseded` 必须带 `superseded_by` 且指向存在的文件。
4. repo 内相对链接必须有效（inbox/、docs/、templates/ 除外）。
5. `INDEX.md` 与 `wiki/` 实际内容一致（脚本重算比对，防手工漂移）。

被删除的字段及去向：`confidence` → 删（status 三态足够）；`review_state` → 并入 status；`id: kb:type:slug` → 文件路径就是 id（git mv 会保留历史，改名时依赖 check 的断链报告）；`type` → 目录即类型（分类法表保留在 `schemas/frontmatter.md`，含 v2 十一类 → v3 六类的映射）；`created_at` → git log；`visibility` → repo 权限即边界，需要更细粒度时再拆库；`claim_refs/memory_*/index_policy/quality` → 删，理由见 01。

### 5.2 sources 约定与链接失效（link rot）

来源处理的总原则：**链接为主，摘录为辅，git 历史兜底**。

1. **编译时定向保险**：capture/成页时把关键证据摘录进正文（"来源摘录"小节）——runbook 步骤的依据、报错原文、结论原话。重要性越高摘得越多。知识本体已编译进页面，外链死亡只损失再核查通道，而通道里最值钱的部分已在摘录里。这是对 raw/ 全量镜像的替代：全额保险 → 定向保险。
2. **sources 条目允许状态注记**：
   ```yaml
   sources:
     - https://confluence.company.com/pages/123456 (moved to .../789, 2026-07)
     - https://jira.company.com/browse/PAY-1234 (dead link as of 2026-07, excerpt preserved in page)
   ```
3. **园艺时处理**：外链被移动 → 更新 URL；被删除/标记过时 → 加注记，检查页面摘录是否足以自立，不足且页面重要 → 标 `needs-review` 交 owner 决定补证。
4. **易失来源**（聊天记录、口述、会议）：原文直接粘进 inbox 条目正文，inbox 文件本身就是 raw；compile 成正式页后原文精华进页面摘录，inbox 文件删除——**git 历史是永久的 raw 层**，任何时候可完整找回并审计。

### 5.3 原始材料的处理（ingest 认知步骤的去向）

砍掉 raw/ 砍的是存储合同（目录 + manifest + sha256），不是 ingest 认知步骤。抽取摘要/事实/关系的工作由 `prompts/capture.md`（单条）和 `prompts/gardening.md`（批量 compile）承担。员工的职责收缩为**把材料递到 agent 面前**（贴 URL / 粘正文 / 丢文件），格式转换与成页是 agent 的活：

| 来源类型 | 供给方式 | 归宿 |
| --- | --- | --- |
| 可链接（Confluence/Jira/事故单） | 贴 URL 或粘正文给 agent；agent 有 Atlassian MCP 等工具时可自取 | wiki 页 + sources 链接 + 关键摘录；原文不落库（源系统就是档案馆） |
| 易失（Teams 讨论/会议/口述） | 粘进 inbox 条目 | inbox 即 raw → compile 后精华入页，git 历史兜底 |

工具集成（Confluence/Jira 的 API/MCP）**属于 agent 客户端层**（每个人自己的 MCP 配置），不属于知识库 repo——repo 永远保持纯文件，任何核心流程都不依赖机器访问外部系统（人在环内可以贴）。

### 5.4 inbox/ 条目

**零必填字段。** 唯一约定：一条知识一个文件，文件名 `YYYY-MM-DD-一句话.md`，开头写清上下文（哪个系统、什么时间、谁在场/相关 ticket）。允许直接 commit 到 main——inbox 的本质是"比 Teams 消息强一点的暂存区"，门槛必须为零。质量在园艺例会上补，不在捕获时卡。

### 5.5 页面正文模板（示例: troubleshooting）

```markdown
---
owner: staff:12345678
updated: 2026-07-07
sources:
  - https://jira.company.com/browse/PAY-1234
tags: [payment]
---

# 支付网关 502 突增 (上游连接池耗尽)

## 现象
<!-- 告警长什么样, 用户侧什么表现, 如何确认是同一问题 -->

## 根因
<!-- 一段话讲清机制 -->

## 处置步骤
<!-- 编号步骤, 每步带验证方式; 高危步骤标注 [需要审批] -->

## 如何预防 / 已做的改进
<!-- 关联的修复 ticket、监控、决策页链接 -->

## 相关页面
<!-- wiki 内相对链接 -->
```

页面写作三条硬规则（写进 AGENTS.md）：**30 秒可扫读**；超过 200 行就拆页；一页只回答一个问题。

## 6. AGENTS.md 设计要点

> AGENTS.md 已作为实际文件落地在仓库根（本节只记录设计决策，避免双份维护漂移）。英文书写（agent 指令的最稳妥语言），手写、≤150 行，只写"agent 猜不到的团队特有约定"；CLAUDE.md 与 `.github/copilot-instructions.md` 均为指向它的一行指针，保证单一事实源。字段细节引用 `schemas/`，不在 AGENTS.md 内复制。

覆盖的内容块：

1. **Layout**：各目录的信任级别（wiki 可信 / inbox unverified / templates、prompts、schemas 的用途）。
2. **Query 协议**（浓缩版，完整版在 `prompts/query.md`）：先读 INDEX → 不够就 grep → 读全文再回答 → 必须引用 → 答不出返回 unknown 并建议建页 → 高价值合成答案主动提议回填 PR。
3. **冲突裁决顺序**（多个候选答案时的确定性优先级）：

   ```text
   1. status 过滤: superseded 跳过(顺 superseded_by 走); needs-review 降级并声明
   2. 位置信任:   wiki/ > inbox/ (引用 inbox 必须声明 unverified)
   3. 领域归属:   问题所属域的 owner 名下页面优先 (依据 team/people.md)
   4. 时效:      updated 更近者优先
   5. 仍平局 =>  两个 current 页面真冲突 = 知识库 bug: 把两个答案连同日期
                 一起呈现给用户, 标 needs-review, 留给园艺例会裁决
   ```

   立场：真冲突必须浮出水面，而不是被一个 confidence 数字静默仲裁掉。
4. **写作规则**：inbox 零门槛可直接 commit；正式页用模板走 PR；30 秒可扫读；>200 行拆页；一页一个问题；先 grep 查重再新建；矛盾不许静默覆盖；关键证据摘录进页面。
5. **外部系统**：有 Confluence/Jira 工具（MCP 等）可自取内容核查，没有就请用户粘贴——工具是增强项，不是依赖。
6. **敏感数据**：不落凭证、不落客户 PII、不整页复制 Confluence（链接 + 摘录代替）。
7. **硬规则**：wiki/ 只经 PR（agent 也不例外）；提 PR 前跑 `npm run check`；绝不编造 sources。

## 7. 多入口接入（不绑定模型/Agent 的具体做法）

| 入口 | 接入方式 | 成本 |
| --- | --- | --- |
| GitHub Copilot Chat (IDE) | `.github/copilot-instructions.md` → "Read AGENTS.md first" ；跨 repo 场景建 **Copilot Space** 挂载本 repo（官方推荐的 markdown 知识库模式） | 10 分钟 |
| 业务 repo 里的 Copilot | 各业务 repo 的 copilot-instructions.md 加一行："团队知识库在 <repo URL>，排障/规范问题先查它" | 每 repo 1 行 |
| Claude Code | 根级 `CLAUDE.md` = "Read AGENTS.md." | 已内建 |
| opencode / Codex 等 | 原生读 AGENTS.md（事实标准） | 零 |
| 公司内部 API 模型 | `prompts/query.md` 作为 system prompt + 把 INDEX.md 和命中页面塞进上下文；后续需要再包一个 20 行的查询脚本 | 按需 |
| 人 (不用 AI 时) | README → INDEX → 页面；GitHub 网页搜索 | 零 |

关键设计：**知识以纯文件形态存在，任何入口都只是"会读文件的客户端"**。不建 MCP server、不建 API——直到出现"某入口确实无法访问 repo 文件"的具体障碍（触发器见 03 Phase 4）。

## 8. staff-id 与人员路由

已确认的口径：**staff-id 是公司内部员工唯一标识，必须保留；GitHub username/email/team 可自由使用。** 由此确定双轨制：

1. **正式知识内的规范身份 = staff-id**：frontmatter `owner`、people.md 主键、页面正文中的人员引用都用 `staff:########`——它在组织内稳定，不随 GitHub 账号变更/离职交接漂移。
2. **工程配置自由使用 GitHub 标识**：CODEOWNERS 用 GitHub team、PR reviewer 用 username、评论里随意。v2 的"知识页之外也禁用 GitHub username"禁令取消。
3. **`team/people.md` 承担双向映射**：staff-id ↔ GitHub username ↔ 负责域/系统。这是 agent 回答"这事该找谁"的唯一依据，也是 owner 字段校验的存在性来源（check.ts 会验证 owner 出现在 people.md 中）。条目 schema 见 `schemas/person.md`。

## 9. Confluence 策略

三阶段，方向与 v1/v2 相反：

1. **现在（Phase 0-1）— 链接优先**：wiki 页面引用 Confluence 就贴 URL。不镜像、不落全文。
2. **按需搬运**：某 Confluence 页被反复查询/引用 → 把它改写（不是复制）成 wiki 页，`sources` 指向原页，并在原 Confluence 页顶部加一行"此内容已迁移至 <repo>，本页停止维护"。知识的权威身份一次只在一处。
3. **触发后（Phase 3）— 反向发布**：当"不用 git 的同事看不到 wiki"成为被抱怨的问题时，用现成工具（如 kovetskiy/mark 或 GitHub Actions marketplace 的 markdown→Confluence 同步）把 `wiki/` 单向发布到一个只读 Confluence space，页脚注明"本页由 git 自动发布，修改请提 PR"。

## 10. 治理机制：双周园艺例会

外部证据一致表明 wiki 死因是所有权与维护惯性，不是工具。v3 的治理只有一个机制：

```text
频率:   每两周 30 分钟 (可并入既有团队例会)
角色:   园丁轮值 (每期 1 人, 团队内轮转)
流程:   1. 会前: 园丁跑 prompts/gardening.md, agent 产出一个 PR:
           - inbox 条目分类: 起草成正式页 / 合并进已有页 / 建议丢弃
           - 健康报告: 过期页 / 断链 / needs-review / 孤儿页
        2. 会上: 10 分钟过 PR, 决定合并/退回; 认领 needs-review 页面
        3. 会后: 合并 PR, 更新 INDEX (脚本)
产出:   知识从 inbox 流入 wiki 的唯一稳定节拍
```

维护成本的设计上限：**每人每两周 ≤ 30 分钟**（园丁 1 小时）。超过即说明机制又在膨胀，砍。

## 11. 度量（只测三个数）

1. **回答率**：本月 agent/人从 wiki 得到答案的问题数 vs unknown 数（园艺例会顺手记一行）。
2. **鲜活度**：`updated` 在 180 天内的页面占比。
3. **贡献面**：过去一个月有 commit/PR 的不同贡献者数。

不建 dashboard。三个数写在园艺 PR 的描述里即可。任何一个数连续两个月恶化，才值得开会讨论机制调整。
