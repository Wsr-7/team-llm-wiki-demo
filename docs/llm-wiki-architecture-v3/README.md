# LLM Wiki Architecture v3 — 设计文档导读

> 产出日期: 2026-07-07
> 前置版本: `design-draft-v1/`（v1）、`docs/llm-wiki-architecture-v2/`（v2）
> 状态: 设计方案（本轮不改造 repo 本体）

## TL;DR

v1/v2 的大方向是对的：**Git 是权威层，markdown 是载体，PR 是审核机制**。
但两版设计合计约 9300 行文档，而 `wiki/` 里只有 2 个 demo 页面。系统为"第 2000 页时才会出现的问题"（claim 级溯源、置信度衰减、混合检索、图谱、OKF 导出）设计了完整治理体系，却没有回答"第一周团队成员周一早上到底怎么用"。

v3 的核心主张一句话：

```text
先让知识存在，再让知识受治理。
贡献一条知识的成本必须低于在 Teams 里问一次人，否则系统必死。
```

具体做法：

1. **砍掉 5 个知识存放区中的 3 个**：`raw/`、`personal/`、`confluence-mirror/` 全部取消，只留 `inbox/`（未审快速捕获）和 `wiki/`(已审正式知识) 两级信任。
2. **候选层 = PR 本身**：`inbox/candidates/` 的六段式候选文档、candidate_status 状态机、review 队列，全部由 GitHub PR / Draft PR / PR 评论天然承担，不再重复建设。
3. **Frontmatter 从 12+ 字段减到 2 个必填**（`owner`、`updated`），溯源用链接（Jira/Confluence/incident URL）而不是 sha256 + 行号锚点。
4. **检索 = INDEX.md + agent grep**，不建 corpus.jsonl / chunks / 向量库。有实测证据表明在几百页规模下这已经够用。
5. **阶段推进用触发器，不用日历**：每个 Phase 有明确的"什么信号出现才升级"，没有信号就停在当前阶段，这是特性不是缺陷。
6. **Confluence 方向反转**：不做 Confluence → repo 的镜像；先"链接优先、按需搬运"，后期做 repo → Confluence 的单向发布（让不用 git 的同事也能看到）。

## 阅读顺序建议

- 想知道"为什么推翻 v2 的大部分机制" → 先读 01。
- 想直接看"v3 长什么样" → 直接读 02。
- 想知道"下周一开始做什么" → 直接读 03 的 Phase 0。
- 对某个被砍掉的概念不服气 → 查 04 的 FAQ，每一条都给了证据或触发器。

## 一条元规则

本套 v3 文档刻意控制在约 1500 行以内。如果未来某次修订让设计文档的行数再次超过 `wiki/` 中真实知识的行数，那就是系统再次跑偏的信号——停止写设计，去写知识。
