# 06 — 对抗性审查与整改状态

> 审查日期: 2026-07-07 / 整改落地: 2026-07-08
> 审查立场: 不设"不动已定架构"的前提——那等于自己给自己划考试范围。发现的问题该改架构就改架构。
> 本轮审查同时纳入一个关键事实修正: **团队规模为 150-200 人**（含前端/后端/架构/business/管理者），
> 此前评审隐含的"5-20 人小团队"适用范围假设是错的, 相关设计已修订（见 §4）。

## 1. 第一性原理: 系统成立的四个必要条件

剥掉所有机制，团队知识库活下来只需要四件事同时为真：

| # | 条件 | v3 的回答 | 承重程度 |
| --- | --- | --- | --- |
| 1 | 有人写（贡献成本 < 感知收益） | inbox 零门槛 + agent 代工 + PR 自合 | 机制充分 |
| 2 | 有人查且信（答案错一次信任塌一半） | PR 人审 + 证据阶梯 + status 三态 | **押注在 review 质量上** |
| 3 | 内容不腐烂（过期速度 < 修正速度） | 双周园艺 + stale 报告 + verified | **押注在园艺存续上** |
| 4 | 扛得住组织现实（流动/挤压/合规） | git/PR 原生 + staff-id + 英文政策 | 机制充分 |

结论先行：**条件 2 和 3 是两面人墙，机制的极限是让人墙的裂缝第一时间可见，不能替代它们。** 本轮整改的主线就是给这两面墙装"裂缝报警器"。

## 3. R2 折衷方案: 证据阶梯（claim_refs 与纯人审之间）

v2 的 claim_refs（行号锚点 + quote_hash）太重，纯 "excerpts + 人审" 又没有强制力。折衷方案是四层全部轻量的**证据阶梯**，本轮已全部落地：

```text
第 1 层  [E#] 证据标记 (markdown 约定, 非 YAML 机制)
         runbook/troubleshooting 的关键步骤标 [E1], 指向 "Source excerpts"
         里的编号摘录 `- [E1] > quote (source: link)`。
         —— 这就是 claim_refs 的语义, 但载体是人能直接读的正文约定。
         落点: templates/runbook|troubleshooting, schemas/frontmatter.md §2

第 2 层  结构校验 (机器兜底)
         runbook/troubleshooting 缺 "## Source excerpts" 小节 → check warning。
         落点: scripts/check.ts

第 3 层  verified 字段 (可执行的信任信号, 不是 confidence 浮点数)
         区分"文本被编辑过"(updated) 和"流程被真实执行验证过"(verified:
         生产执行/演练/事故实战的日期)。园艺按 verified(缺省回退 updated)
         > 90 天报告 runbook 过期——文本新鲜但从未执行过的 runbook 一样过期。
         落点: schemas/frontmatter.md, check.ts, prompts/gardening.md

第 4 层  Unevidenced claims 自报 (把橡皮章成本降为核对清单)
         agent 起草的正式页 PR 必须在描述中列出"没有 [E#]/来源支撑的结论"
         (全有证据则写 none)。reviewer 从"通读全文找错"变为"核对清单+抽查
         一个 [E#]"。PR 模板加了对应的 reviewer check 项。
         落点: prompts/capture|gardening.md, PULL_REQUEST_TEMPLATE.md, AGENTS.md
```

与 claim_refs 的对比：语义保留了 90%（结论↔证据的显式映射 + 验证时效），成本砍掉了 90%（无 schema 机器、无哈希、无行号维护、人可直接读写）。放弃的 10% 是"来源被篡改的密码学证明"——内部 Jira/Confluence 自带历史，该威胁模型不成立（01 §P4 的结论不变）。

## 4. 规模修正: 150-200 人团队

此前"5-20 人"的隐含假设错了。修正后的参与模型和设计变更：

```text
错误模型: 全员建设、全员 review、一半成员贡献才算成功
正确模型: 供给侧 20-40 名种子/活跃贡献者 + 消费侧全员 (200 人)
          "不是所有人都参与建设"不是风险, 是常态和健康形态
```

由此产生的设计变更（均已落地）：

1. **域级 CODEOWNERS 提前为必做**（Step 0.3），否则 R7 在此规模下必然发生。
2. **种子与验收指标重定**：种子队 15-25 人（每域至少 1 人，含非开发试读者）；Phase 0 验收 ≥15 页；Phase 1 验收改为"活跃贡献者 ≥15 人"（原"一半团队成员"在 200 人语境下 = 100 人，荒谬）。
3. **园艺扩容路径**：单场例会撑到 inbox 每周期积压 >15 条，之后按域拆分为并行的域级 gardening PR（同一协议）；治理分层 = 2-3 admin → 域 owner → 园丁轮转（02 §10）。
4. **读侧优先级上调**：非 git 用户（business/管理者）占消费侧多数，Phase 3（Confluence 单向发布）预期第一季度内触发，从"可能永远不做"改为"计划内、等触发即执行"。
5. **规模触发器提前预警**：200 人组织的知识产出速度下，T2（~150-200 页）可能在 6-12 个月内到达，检索层（qmd/BM25）的评估可以在 Phase 1 后期就开始积累 miss 记录。

## 6. 生产级判定（修订）

**判定：对 150-200 人内部组织的团队知识库场景，完成 Phase 0 TODO（CODEOWNERS 真实化 + branch protection + bot bypass + 真实 people.md）后，达到企业生产级。**

- 生产级要件核对：访问控制（repo 权限）✓｜审计（git/PR 历史）✓｜防泄漏（政策 + push protection，待开启）✓｜可用性（GitHub）✓｜可恢复（纯文件全量可重建）✓｜维护停摆可见（watchdog）✓。
- **仍然明确不够格的场景**：受限/合规敏感知识域（等 R12 触发后按第二 repo 模式扩展）；监管级知识管理（需要强制溯源与留存策略，超出本系统定位）；跨组织知识交换（OKF 导出，T4 触发后一天工作量）。
- 最终的一句实话：这套系统的纸面架构已经简单到"没有多少东西可以坏"；它真实的存活概率取决于两件仓库外的事——**管理层是否给园丁和 review 留出预算内的时间，以及事故关单流程是否愿意挂接 inbox**。这两件事有了，8 分设计能跑出 9 分效果；没有，9 分设计也一样死。
