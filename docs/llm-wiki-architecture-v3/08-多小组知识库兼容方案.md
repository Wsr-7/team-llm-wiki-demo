# 08 — 小组知识域方案（单库分域）

> 问题: 150-200 人的大团队下有多个小组（业务 squad / 前端 / 后端 / 架构 / business…），
> 小组想要"自己的知识库"时怎么办？
>
> 立场（发起人已定）: **小组的知识也是整个团队的知识。** 所以答案不是给每个小组一个库，
> 而是给每个小组一个"域"——同一个库里的一块有主之地。分库只作为权限隔离的极端例外（附录 A）。
>
> 修订记录: 2026-07-23 v1 曾提出 Hub-and-Spoke 三级承载；同日按发起人反馈收敛为
> 单库分域为主体，原二三级（域视图 / spoke 库）弱化——前者并入 §3 的可选便利，
> 后者降为附录 A。本文属超前期探讨，落地细节待种子期后校准。

## 1. 域模型：domain 是与 type 正交的第二轴

仓库的第一轴是**类型**（目录即类型，schemas/frontmatter.md 的分类法）；小组引入第二轴**域**（domain），表现为各类型目录下的同名子目录：

```text
wiki/
├── troubleshooting/
│   ├── payment/          ← payment 组的排障页
│   └── checkout/
├── runbooks/
│   ├── payment/          ← 同一个域 slug 贯穿所有类型
│   └── infra/
├── systems/
│   └── payment/
│       └── payment-gateway.md   ← 域主页（见 §3）
└── decisions/
    └── payment/
```

域命名三条约定：

1. **slug 小写短词**（`payment` / `checkout` / `infra` / `fe-platform`），跨类型必须一致。
2. **注册处 = `team/people.md` 的 `owns` 列**——一个域存在的标志是有人在 owns 列认领它。不新增注册文件。
3. **≥3 页同域才开子目录**，之前平铺在类型目录下（避免一页一目录的空壳）。`check.ts` 对子目录深度无限制，无需改动。

## 2. 小组在域内得到什么（这就是"小组知识库"）

| 诉求 | 域内的实现 | 成本 |
| --- | --- | --- |
| "我们的内容我们说了算" | CODEOWNERS 一行：`/wiki/**/payment/ @org/payment-team`——该域全部类型的页面由本组 review（平台不支持 `**` 时退化为按类型逐行） | 1 行 |
| "我们有自己的入口" | **域主页 = 该域的 system 页**：`wiki/systems/<domain>/` 下的主系统页在 Related pages 汇总本域的 runbooks / troubleshooting / decisions。人和 agent 都从这里进 | 已有模板 |
| "我们自己维护自己的" | **域园丁**：园艺按域拆分时，各域产出自己的 `gardening: <domain> YYYY-MM-DD` PR（标题仍以 `gardening:` 开头，watchdog 的 grep 不需要任何改动） | 轮值表加一列 |
| "我们要看自己的健康度" | 域级 gardening PR 的 Metrics 天然就是域级度量；hub 级园艺只看总账 | 零 |
| "AI 只查我们的东西" | 可选便利：挂 `wiki/*/payment/` 路径的 Copilot Space；或提问时带域名，agent 按路径过滤。不是必需品——跨域可见恰恰是单库的红利 | 可选 |

## 3. 小组能自定什么、不能自定什么

```text
能（域内自治）:                          不能（全库契约, 改动走 schemas/ PR）:
- 域内再分子目录 (如 runbooks/payment/   - 类型分类法 (六类 + glossary)
  batch/ 与 online/)                     - frontmatter 七字段 schema
- tags 词汇                              - 语言政策 (正式内容英文)
- 种子选题与优先级                        - check 规则与 PR-only 红线
- 域园艺节拍 (可以更密, 不可低于双周)      - AGENTS.md 协议
```

这条分界线就是"兼容性"的全部：**小组的自由在内容和节奏，不在结构和规则。** 结构统一换来的是：一个 INDEX、一次 grep、一套 CI、跨域引用就是普通相对链接、跨域冲突走既有五级裁决——全部免费。

## 4. inbox 与域的关系

inbox **保持扁平，不分域**——零门槛优先，捕获时不该让人思考"归哪个组"。路由发生在园艺侧：条目正文里的系统名/ticket 就是路由依据，各域园丁在 triage 时认领自己的条目，无人认领的由当期 hub 园丁兜底。inbox 每周期积压 >15 条再讨论拆分（02 §10 既有触发器，优先拆的是**园艺**而不是 inbox 目录）。

## 5. 新域开通 checklist（约 15 分钟）

```text
□ 1. team/people.md: 小组成员的 owns 列登记域 slug, 指定域园丁 (notes 列)
□ 2. CODEOWNERS 加一行: /wiki/**/<domain>/ @org/<team>
□ 3. 建域主页: wiki/systems/<domain>/<main-system>.md (system 模板,
     Related pages 即域目录)
□ 4. 种子 1-2 页 (troubleshooting/runbook 优先) 挂到域子目录
□ 5. 域园丁进入轮值; 无需任何 CI / 脚本 / 结构改动
```

## 6. 何时需要动机制（触发器，均已有既有出口）

| 信号 | 动作 | 出口 |
| --- | --- | --- |
| inbox 每周期积压 >15 条 | 园艺按域拆分为并行 PR | 02 §10 |
| 域多到 INDEX 单文件难读（~150-200 页） | INDEX 按域加分组（build-index 小改）或引入检索 | 03 Phase 2 (T2) |
| 某域出现"不能全员可见"的内容 | 附录 A 的权限例外评估 | 06 §R12 |
| 小组要求偏离结构/schema | 拒绝；确有普适价值则走 schemas/ PR 全库生效 | schemas/README |

## 附录 A — 极端例外：权限隔离时的独立库（弱化保留）

唯一正当的分库理由是 **权限边界**（存在确实不能全员可见的知识，06 §R12 预留的场景）。"体量大""想要自治""分类不同"都不是——它们在 §2/§3/§6 里已有域内出口。

若该例外真的发生（预期概率低）：

1. hub 的 `wiki/decisions/` 先写一页建库决策（内容范围 + owner + 为什么域内放不下）。
2. 新库通过 GitHub template 从 hub 实例化，**同构不走样**：同分类法、同 schema、同 AGENTS.md、同 check/CI、同语言政策；库设 private + 白名单。
3. hub 侧留可见的指针：`team/people.md` 的 notes 列注明"<domain> 的受限内容在 <repo>（申请访问找 staff:XXXXXXXX）"——不建注册表文件、不建跨库聚合，除非例外库超过一个。
4. 该库内容一旦不再敏感，归并回 hub 域子目录并关库。**例外库的默认命运是被归并，不是长存。**
