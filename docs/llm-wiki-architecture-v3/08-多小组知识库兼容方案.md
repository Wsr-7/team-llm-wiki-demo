# 08 — 多小组知识库兼容方案

> 问题: 150-200 人的大团队下有多个小组（业务 squad / 前端 / 后端 / 架构 / business…），
> 小组想要"自己的知识库"时怎么办？如何与大团队库兼容？
> 立场先行: **默认答案是"不建分库"——单库分域已经覆盖 90% 的小组诉求。**
> 分库是触发式的例外，且必须满足同构契约。本文定义: 什么时候分、怎么分、分了以后怎么保持兼容。

## 1. 三个选项

| | A. 单库分域（现状即支持） | B. 每组一库（联邦） | C. Hub-and-Spoke（推荐） |
| --- | --- | --- | --- |
| 形态 | 一个 org 库，小组 = `wiki/<type>/<domain>/` 子目录 + 域级 CODEOWNERS + 域级园艺 | 每个小组一个同构库，org 库只是其中之一 | **常态 = A**；仅在触发器命中时为该小组开 spoke 库，org 库为 hub |
| 检索/消费 | 一个 INDEX、一次 grep，跨组知识免费可达 | agent 要知道去哪个库找；N 个入口 | hub 默认；spoke 通过注册表被发现 |
| 权限 | 单一层级（全员可见） | 每库独立（可私有） | hub 全员可见；需要隔离的内容才进 spoke |
| 治理成本 | 1 套园艺/CI/watchdog | N 套，且各库质量参差 → 碎片化回到 Confluence 老路 | 1 + 触发的少数几套 |
| 知识重复/冲突 | check 与园艺可管 | 跨库无人管，必然漂移 | 放置规则 + 晋升路径约束 |
| 失败模式 | PR 噪音集中；小组无自治感 | **重演痛点本身**："资料散落各处"只是从 Confluence 换成了 N 个 repo | spoke 泛滥（靠反触发器挡） |

选 B 的本质风险值得点破：这个项目的出发点就是"知识散落各处"。**无节制的每组一库 = 用 git 重新发明散落**。所以 B 只能作为受控例外存在，这就是 C。

## 2. 推荐方案：Hub-and-Spoke

```text
                    ┌────────────────────────────────┐
                    │  HUB: team-llm-wiki (org 库)    │
                    │  - 跨组知识 (默认归宿)           │
                    │  - glossary / people.md (权威)  │
                    │  - team/repos.md (spoke 注册表) │
                    │  - 控制面规范源 (schemas/prompts)│
                    └──────┬─────────────────┬───────┘
            域子目录(常态)  │                 │  同构契约
   ┌───────────────────────┴──┐      ┌───────┴────────────────┐
   │ wiki/runbooks/payment/   │      │ SPOKE: payment-sec-wiki │
   │ wiki/systems/checkout/   │      │ (触发: 权限隔离)         │
   │ ...(小组=域, 不是库)      │      │ 同结构/同schema/同check  │
   └──────────────────────────┘      └────────────────────────┘
```

### 2.1 小组的三级承载（按序使用，能停在低级就停）

1. **域子目录**（默认，零成本）：`wiki/<type>/<domain>/` + 一行域级 CODEOWNERS + 认领一个域园丁。小组获得：自己的 owner 权、自己的审核权、按域拆分的园艺 PR。这已经是"小组知识库"——只是和别人共享一个 repo 外壳。
2. **域视图**（低成本，按需）：INDEX 本就按目录分节；小组要"自己的入口"，给它一个 `wiki/<type>/<domain>/` 的 GitHub 目录链接或 Copilot Space（Space 可只挂目录级路径）即可，不需要新库。
3. **Spoke 库**（触发式例外）：见 §3 触发器。

### 2.2 知识放置决策树（一问测试）

```text
这条知识, 隔壁组的人 oncall / 接手 / 排障时可能需要吗?
  ├─ 可能 → hub (org 库), 放对应域子目录          ← 绝大多数
  └─ 不可能, 纯组内 →
       ├─ 内容有权限敏感性(仅组内可见) → 该组 spoke 库 (无则触发建库评估)
       └─ 无敏感性 → 仍然放 hub 的域子目录
          (纯组内但不敏感的知识放 hub 没有任何代价, 反而白得跨组可见性)
```

## 3. Spoke 建库触发器与反触发器

**触发器**（满足任一才允许建 spoke）：

| # | 触发器 | 说明 |
| --- | --- | --- |
| T-S1 | **权限边界** | 该组存在"不能全员可见"的知识（安全流程、敏感运营数据）——这正是 06 §R12 预留的"第二个 repo"模式 |
| T-S2 | **体量压垮** | 该组的 inbox/PR 量在域级园艺拆分之后仍然拖垮 hub 节拍（量化参考：该域连续 3 个周期贡献 hub 一半以上的 inbox 条目） |
| T-S3 | **组织边界** | 该"小组"实际是另一个管理单元（独立预算/独立管理链），hub 团队无法为其内容背书 |

**反触发器**（这些理由一律拒绝，引导回域子目录）：

- "我们想要自己的空间/自治感" → 域子目录 + 域 CODEOWNERS 就是自治。
- "我们的分类不一样" → 分类法是兼容契约的一部分（§4），域内可加子目录，不可另起分类。
- "建库很容易" → 建库容易，**养库难**——每个 spoke 意味着独立的园丁轮值、watchdog、种子动员。批准 spoke 前该组必须先指定园丁和 2 名以上种子贡献者。

审批人：knowledge admins。评估记录以 decision 页写入 hub（`wiki/decisions/`），这本身就是一条团队知识。

## 4. 同构契约（Conformance Profile）

Spoke 与 hub 的兼容不靠联邦基建，靠**同构**——克隆同一套结构与规则。一个库是"team-llm-wiki 兼容"的，当且仅当：

```text
C1  目录分类法一致: wiki/{troubleshooting|runbooks|systems|decisions|concepts|guides}
    + glossary.md + inbox/ + team/people.md (仅本组成员)
C2  frontmatter 七字段 schema 一致 (schemas/frontmatter.md), 不增不改
C3  AGENTS.md 协议一致 (从 hub 复制; CLAUDE.md / copilot-instructions.md 指针同款)
C4  scripts/check.ts + build-index.ts 原样复制, CI 绿色 (Jenkinsfile 同款, J1 必配)
C5  语言政策一致 (正式内容英文, inbox 任意)
C6  在 hub 的 team/repos.md 注册 (见 §5.1), 并声明本库 scope
```

落地方式：把 hub 设为 **GitHub template repository**（一次设置），spoke 用 "Use this template" 生成后按 §7 checklist 裁剪。**不用 git submodule/subtree 同步控制面**——为 2-3 个 spoke 引入子模块复杂度不值得；控制面漂移靠 §6 的版本行 + 园艺检查兜住。

> 与 01 §3.3（OKF 裁决）的关系：当年说"出现第二个消费方再考虑交换格式"。现在内部第二消费方出现了，
> 答案依然不是 OKF 导出层——**同构克隆让交换格式问题根本不存在**（两边本来就是同一种格式）。
> OKF 仍然只在"外部组织、无法要求同构"时才有意义。裁决不变。

## 5. 跨库机制（每条都刻意便宜）

### 5.1 发现：注册表，不是聚合服务

hub 新增单文件 `team/repos.md`（首个 spoke 出现时创建）：

```markdown
| repo | scope | owner | visibility | notes |
| --- | --- | --- | --- | --- |
| <hub URL> | org-wide knowledge | @org/knowledge-admins | org | hub |
| <spoke URL> | payment security procedures | staff:XXXXXXXX | restricted | T-S1 |
```

agent 跨库消费方式：hub 的 AGENTS.md 加一行（首个 spoke 出现时才加，遵守"只减不增"需挤占）："If the answer may live in a sub-team wiki, check `team/repos.md` and search the repos you can access." Copilot 场景更简单：一个 Space 同时挂 hub + 可见的 spoke（Space 支持多 repo）。**不建跨库检索服务**——那是 Phase 4 触发器的事。

### 5.2 晋升：spoke → hub

与"个人知识 → 团队知识"完全同构：**想成为 org 知识的那一刻 = 向 hub 发 PR**（agent 代做，sources 注明 spoke 原页 URL）。合并后 spoke 侧删除原页（git 历史保留），或在受限内容场景保留 spoke 版并在 hub 版脱敏。

### 5.3 取代：跨库不用 superseded_by

`superseded_by` 是库内相对路径（check 校验文件存在），跨库不适用。跨库取代约定：**删除被取代方**（git 历史即档案）+ 合并 commit message 注明去向 URL。不为跨库场景扩展 schema。

### 5.4 冲突：hub 优先

同一主题 hub 与 spoke 都有页面且矛盾时，裁决顺序在 02 §6 的五级之前加一级：**hub 版本优先**（org 背书 > 组内背书）。spoke 侧应晋升差异或删除本地版。

### 5.5 治理：各库自治，hub 看总账

每个 spoke 自带完整治理（自己的园丁轮值、gardening PR、J1/J3 CI——jenkins/ 下的文件原样复用）。hub 的园艺例会每期多看一眼：registry 里各 spoke 的最近 gardening 日期（一行 git log 的事），连续停摆的 spoke 由 admin 找其 owner——**spoke 死亡的处置是归并回 hub 域子目录，不是放任成僵尸库**。

## 6. 控制面版本与漂移控制

- `schemas/README.md` 增加一行协议版本（如 `protocol: v3.1`），控制面（schemas/prompts/templates/scripts/AGENTS.md）每次实质变更时递增并在 hub 记 changelog（一行）。
- spoke 园艺 checklist 加一项："对照 hub 的 protocol 版本，落后则同步复制控制面文件"（纯文件复制，双周一次，5 分钟）。
- 允许的漂移：模板正文措辞、域子目录划分。不允许的漂移：C1-C5 任何一条。

## 7. Spoke 建库 checklist（触发器命中后，约 1 小时）

```text
□ 1. hub 的 wiki/decisions/ 写一页建库决策 (触发器编号 + scope + owner)
□ 2. "Use this template" 生成新库; 清空示例内容 (inbox 示例条目 / glossary 示例词条)
□ 3. team/people.md 填本组成员; CODEOWNERS 填本组 team; 语言/schema 不动
□ 4. Jenkins 建 J1 (必) / J3 (建议) — 指向本库, jenkins/ 文件已在模板里
□ 5. 开 branch protection (docs/branch-protection.md 同款)
□ 6. 在 hub 的 team/repos.md 注册; 首个 spoke 时同步在 hub AGENTS.md 加跨库一行
□ 7. 指定园丁 + ≥2 名种子贡献者, 各写 1-2 页种子内容
□ 8. (T-S1 场景) 库设为 private + 白名单; 确认 restricted 内容不进任何共享 Space
```

## 8. 后期触发器（本文明确不做，信号出现再说）

| 信号 | 动作 |
| --- | --- |
| spoke ≥3 个且"不知道去哪个库找"成为例会实际抱怨 | 聚合 INDEX（一个脚本拉各库 INDEX.md 合并成 org 总目录，仍是纯文件） |
| 跨库检索需求程序化（内部模型/客服要一次查多库） | Phase 4 查询服务的输入面从单库扩为 registry 列出的多库——检索原语契约不变 |
| 出现无法要求同构的外部消费组织 | 届时再评估 OKF 导出（01 §3.3 触发器原样有效） |
| spoke 数量 >5 | 停下来复盘：大概率是反触发器失守，先归并再扩张 |
