# 分阶段实施计划 (Phase-By-Phase Implementation Plan)

> 目的：从 Phase 0 开始的更完整的分步实施计划。
> 原则：在知识库变得可信之前，不要增加更智能的检索。

## 阶段概览 (Phase Overview)

| 阶段 (Phase) | 名称 (Name) | 主要成果 (Main Outcome) |
| --- | --- | --- |
| Phase 0 | 基线加固 (Baseline Hardening) | 现有骨架变得可检查且由 CI 强制保障 |
| Phase 0.5 | 生命周期与溯源 (Lifecycle And Provenance) | 源哈希、审阅队列、声明引用、置信度规则 |
| Phase 1 | 最小可用团队 Wiki (Minimum Usable Team Wiki) | 真正的 raw → candidate → wiki 工作流，包含所有者审阅 |
| Phase 2 | 搜索与查询评估 (Search And Query Evaluation) | 搜索语料库、分块、查询评估、安全查询工作流 |
| Phase 3 | 图谱与影响导航 (Graph And Impact Navigation) | 确定性图谱 sidecar 及相关/影响查询 |
| Phase 4 | OKF 互操作性 (OKF Interoperability) | 生成 OKF 兼容包和静态查看器路径 |
| Phase 5 | 自动化与结晶 (Automation And Crystallization) | 事件日志、会话结晶、自动化 PR 提案 |
| Phase 6 | 平台接口 (Platform Interface) | 只读 MCP/API 网关和仪表盘 |

## Phase 0: 基线加固 (Baseline Hardening)

### 目标 (Goal)

使当前仓库内部一致、可强制约束且可安全演进。

### Step 0.1: 定义正式检查范围 (Define Formal Check Scope)

任务 (Tasks):

```text
1. 在 scripts/lib/paths.ts 中创建中心路径策略。
2. 在常规检查中仅包含正式知识和控制路径。
3. 从正式检查中排除与 design-draft 和 html-ppt 相关的内容。
4. 仅在需要时添加单独的文档检查。
```

验收标准 (Acceptance criteria):

```text
npm run check 不会因为展示资源或设计示例而失败。
正式检查不会忽略真实的 wiki/raw/inbox/schema 问题。
```

### Step 0.2: 替换 Frontmatter 解析器 (Replace Frontmatter Parser)

任务 (Tasks):

```text
1. 添加一个真正的 YAML 解析器。
2. 添加 JSON Schema 验证器。
3. 重构 check-frontmatter、check-candidates、check-person-files、check-source-refs 以使用共享解析器。
4. 正确验证嵌套的 frontmatter。
```

验收标准 (Acceptance criteria):

```text
嵌套的 frontmatter 结构被正确解析。
无效的 schema 会确定性失败。
现有的演示文件要么通过，要么因明确的错误而有意失败。
```

### Step 0.3: 添加真实源清单检查 (Add Real Source Manifest Check)

任务 (Tasks):

```text
1. 实现 scripts/check-source-manifests.ts。
2. 验证 manifest/source 对的存活性。
3. 验证 id/path 约定。
4. 为 source.md 计算真实的 sha256。
5. 如果 manifest 哈希与 source.md 不匹配则失败。
```

验收标准 (Acceptance criteria):

```text
每个原始源都有有效的 manifest.md 和 source.md。
每个 manifest 都有真实的源哈希。
```

### Step 0.4: 修复演示页面状态语义 (Fix Demo Page Status Semantics)

任务 (Tasks):

```text
1. 决定演示页面是否保留在 wiki/ 中。
2. 如果是，将它们标记为 draft 或 production_applicable=false。
3. 确保查询规则对非生产页面发出警告。
```

验收标准 (Acceptance criteria):

```text
除非查询规则识别 production_applicable=false，否则没有任何标记为 active/reviewed 的页面可以同时声明它不是真实的操作指南。
```

### Step 0.5: 添加 CI 工作流 (Add CI Workflow)

任务 (Tasks):

```text
1. 添加 .github/workflows/lint.yml。
2. 运行 npm run check。
3. 记录本地和 CI 命令。
```

验收标准 (Acceptance criteria):

```text
如果检查失败，PR 无法合并。
```

### Step 0.6: 替换占位符 CODEOWNERS (Replace Placeholder CODEOWNERS)

任务 (Tasks):

```text
1. 将 @org 占位符替换为真实的 GitHub 团队，或仅用于演示的记录在案的占位符。
2. 将 schema/管理员所有权与领域所有权分离。
```

验收标准 (Acceptance criteria):

```text
CODEOWNERS 可以在目标 GitHub 组织中激活，而不会出现静默不匹配。
```

### Step 0.7: 添加分支保护说明 (Add Branch Protection Instructions)

任务 (Tasks):

```text
1. 使用精确的必需设置更新 docs/branch-protection.md。
2. 包含必需的 CI 检查名称。
3. 包含 CODEOWNERS 审查要求。
```

验收标准 (Acceptance criteria):

```text
仓库管理员可以根据文档配置分支保护，无需猜测。
```

## Phase 0.5: 生命周期与溯源加固 (Lifecycle And Provenance Hardening)

### 目标 (Goal)

防止 wiki 变成过时或无法验证的文档堆。

### Step 0.5.1: 构建并检查索引 (Build And Check Index)

任务 (Tasks):

```text
1. 实现 scripts/build-index.ts。
2. 实现 scripts/check-index.ts。
3. 根据 wiki frontmatter 生成 indexes/INDEX.md。
4. 明确将页面标记为 stale、superseded 或 draft。
```

验收标准 (Acceptance criteria):

```text
每个 wiki 页面都出现在生成的索引中。
索引条目与页面标题、id、状态和类型匹配。
手动漂移可被检测到。
```

### Step 0.5.2: 构建审阅队列 (Build Review Queue)

任务 (Tasks):

```text
1. 实现 scripts/check-review-after.ts。
2. 实现 scripts/build-review-queue.ts。
3. 检测已过期的 review_after。
4. 检测缺失的所有者。
5. 检测低置信度的 active 页面。
6. 检测 disputed 页面。
```

验收标准 (Acceptance criteria):

```text
indexes/REVIEW_QUEUE.md 可以从仓库状态生成。
已过期的 active 页面在审阅队列中可见。
```

### Step 0.5.3: 强制置信度规则 (Enforce Confidence Rules)

任务 (Tasks):

```text
1. 实现 scripts/check-confidence-rules.ts。
2. 将 confidence-rules.md 编码为机器可检查的约束。
3. 严重违规则失败。
4. 轻微违规则警告。
```

验收标准 (Acceptance criteria):

```text
review_state=disputed 不能有超过 0.60 的 confidence。
active 页面需要 source_refs。
superseded 页面需要 superseded_by。
```

### Step 0.5.4: 为高风险页面添加声明引用 (Add Claim References For High-Risk Pages)

任务 (Tasks):

```text
1. 添加 schemas/claim-ref.schema.json。
2. 使用可选的 claim_refs 更新 runbook 和决策模板。
3. 为一个 runbook claim 添加示例。
4. 添加脚本来验证 claim refs 指向现有的源和行范围。
```

验收标准 (Acceptance criteria):

```text
至少有一个 runbook 包含有效的 claim_ref。
Claim refs 可根据源路径和行范围进行验证。
```

### Step 0.5.5: 添加替代审阅 (Add Supersession Review)

任务 (Tasks):

```text
1. 实现 scripts/check-superseded-references.ts。
2. 为替代通知添加模板。
3. 为 supersede-page 或扩展 prepare-wiki-patch 添加提示。
```

验收标准 (Acceptance criteria):

```text
如果没有明确的历史说明，active 页面不能将 superseded 页面作为当前指南使用。
```

### Step 0.5.6: 添加矛盾审阅 (Add Contradiction Review)

任务 (Tasks):

```text
1. 添加 inbox/reviews/contradictions/.gitkeep。
2. 添加 templates/contradiction-review.md。
3. 添加 prompts/resolve-contradiction.md。
```

验收标准 (Acceptance criteria):

```text
矛盾可以在不直接编辑 active wiki 页面的情况下被表达。
```

## Phase 1: 最小可用团队 Wiki (Minimum Usable Team Wiki)

### 目标 (Goal)

通过手动控制的循环将系统用于真正的团队知识。

### Step 1.1: 添加真实源材料 (Add Real Source Material)

任务 (Tasks):

```text
1. 选择 3-5 个安全可存储在仓库中的真实内部来源。
2. 将它们添加到 raw/ 下并附上真实的 manifest。
3. 运行来源检查。
```

验收标准 (Acceptance criteria):

```text
至少 3 个真实来源文件夹通过来源 manifest 验证。
```

### Step 1.2: 手动运行摄取和编译 (Run Ingest And Compile Manually)

任务 (Tasks):

```text
1. 使用 prompts/ingest-source.md 创建候选内容。
2. 使用 prompts/compile-wiki.md 生成 Wiki Proposal 章节。
3. 添加质量说明和未解决的问题。
```

验收标准 (Acceptance criteria):

```text
至少存在 3 个包含 Source Understanding 和 Wiki Proposal 章节的候选内容。
```

### Step 1.3: 准备 PR 就绪的 Wiki 补丁 (Prepare PR-Ready Wiki Patches)

任务 (Tasks):

```text
1. 使用 prepare-wiki-patch 协议。
2. 创建或更新正式的 wiki 页面。
3. 更新生成的索引和审阅队列。
4. 运行所有检查。
```

验收标准 (Acceptance criteria):

```text
至少 2 个正式 wiki 页面通过 PR 审查合并。
```

### Step 1.4: 建立所有者审阅习惯 (Establish Owner Review Habit)

任务 (Tasks):

```text
1. 分配真实的所有者。
2. 领域页面需要所有者审批。
3. 将未解决的问题记录在 inbox/reviews 中。
```

验收标准 (Acceptance criteria):

```text
没有 active 的正式页面包含占位符所有者。
```

### Step 1.5: 查询协议试用 (Query Protocol Trial)

任务 (Tasks):

```text
1. 提出 10 个真实的团队问题。
2. 使用 query-wiki 协议回答。
3. 记录未知项和候选机会。
```

验收标准 (Acceptance criteria):

```text
答案引用 wiki 页面和 source refs。
未知项产生候选或来源建议。
```

## Phase 2: 搜索与查询评估 (Search And Query Evaluation)

### 目标 (Goal)

从浏览 wiki 页面转向经过评估的查询支持。

### Step 2.1: 创建查询评估集 (Create Query Evaluation Set)

任务 (Tasks):

```text
1. 添加 indexes/QUERY_EVAL.md。
2. 包含 20-50 个代表性查询。
3. 针对每个查询，列出预期的页面 id 和禁止使用的页面。
```

验收标准 (Acceptance criteria):

```text
搜索变更可以通过稳定的查询集进行评估。
```

### Step 2.2: 构建搜索语料库 (Build Search Corpus)

任务 (Tasks):

```text
1. 实现 build-search-corpus.ts。
2. 包含 wiki 页面、个人资料和索引。
3. 默认排除 raw、inbox、个人 raw/wiki 和 mirror。
4. 附加 status、review_state、confidence、owners、tags 和 source_refs。
```

验收标准 (Acceptance criteria):

```text
indexes/search/corpus.jsonl 被生成且具有确定性。
```

### Step 2.3: 构建分块清单 (Build Chunk Manifest)

任务 (Tasks):

```text
1. 实现 build-chunks.ts。
2. 按标题分割页面。
3. 生成稳定的 chunk id。
4. 追踪哈希和来源元数据。
```

验收标准 (Acceptance criteria):

```text
indexes/search/chunks.jsonl 被生成且具有确定性。
```

### Step 2.4: 实现搜索封装器 (Implement Search Wrapper)

任务 (Tasks):

```text
1. 实现 scripts/search.ts。
2. 从词法搜索和 rg 回退开始。
3. 返回带有页面/分块元数据的排序结果。
```

验收标准 (Acceptance criteria):

```text
查询返回包含 status/confidence/source 元数据的结构化结果。
```

### Step 2.5: 评估搜索 (Evaluate Search)

任务 (Tasks):

```text
1. 实现 evaluate-search.ts。
2. 衡量 hit@5。
3. 衡量 stale/superseded 误用。
4. 手动或半自动衡量未知正确性。
```

验收标准 (Acceptance criteria):

```text
在引入向量搜索之前，搜索有一个基线评分。
```

### Step 2.6: 后续添加混合搜索 (Add Hybrid Search Later)

任务 (Tasks):

```text
1. 仅在词法基线存在后才添加向量搜索。
2. 在图 sidecar 存在后才添加图种子结果。
3. 使用 reciprocal rank fusion 融合词法、向量和图结果。
```

验收标准 (Acceptance criteria):

```text
混合搜索在不增加过时内容误用的情况下改进了查询评估。
```

## Phase 3: 图谱与影响导航 (Graph And Impact Navigation)

生成确定性图谱 sidecar 并支持影响/相关查询。

### Step 3.1: 导出节点 (Export Nodes)

任务 (Tasks):

```text
1. 实现 export-nodes.ts。
2. 包含 wiki 页面、个人资料和来源 manifest。
3. 包含 type、title、path、status、confidence、owners。
```

验收标准 (Acceptance criteria):

```text
graph/nodes.jsonl 可以根据仓库状态重建。
```

### Step 3.2: 导出边 (Export Edges)

任务 (Tasks):

```text
1. 实现 export-edges.ts。
2. 生成 owns、maintains、wikilink、backlink、shared_source、related_to、supersedes。
3. 每条边都包含原因和证据。
```

验收标准 (Acceptance criteria):

```text
graph/edges.jsonl 仅包含可解释的边。
```

### Step 3.3: 添加图谱报告 (Add Graph Report)

任务 (Tasks):

```text
1. 生成 graph/graph-report.md。
2. 报告孤立页面、缺失的反向链接、孤立的所有者、过时的集群。
```

验收标准 (Acceptance criteria):

```text
无需图数据库即可看到图健康状况。
```

### Step 3.4: 添加静态图谱查看器 (Add Static Graph Viewer)

任务 (Tasks):

```text
1. 实现 render-graph-html.ts。
2. 生成 graph/viz.html。
3. 支持按 type、status、owner、confidence 进行过滤。
```

验收标准 (Acceptance criteria):

```text
团队成员可以在没有后端的情况下在本地检视图谱。
```

## Phase 4: OKF 互操作性 (OKF Interoperability)

### 目标 (Goal)

导出可移植的 OKF 兼容包，同时不弱化内部 schema。

### Step 4.1: 定义 OKF 导出配置文件 (Define OKF Export Profile)

任务 (Tasks):

```text
1. 编写 schemas/okf-export-profile.md。
2. 将内部类型映射到 OKF 类型字符串。
3. 将内部字段映射到 x-team-* 扩展。
```

验收标准 (Acceptance criteria):

```text
导出规则已文档化且具有确定性。
```

### Step 4.2: 实现导出 (Implement Export)

任务 (Tasks):

```text
1. 实现 export-okf.ts。
2. 生成 okf/index.md 和 okf/log.md。
3. 将内部链接转换为标准 markdown 链接。
4. 排除受限/机密页面，除非策略允许。
```

验收标准 (Acceptance criteria):

```text
okf/ 可以重新生成并通过 OKF 符合性基础检查。
```

### Step 4.3: 验证导出 (Validate Export)

任务 (Tasks):

```text
1. 检查每个 OKF 概念都有 frontmatter 和 type。
2. 检查 index/log 结构。
3. 根据 OKF 容忍损坏的链接，但报告它们。
```

验收标准 (Acceptance criteria):

```text
OKF 导出对外部代理和查看者有用。
```

## Phase 5: 自动化与结晶 (Automation And Crystallization)

### 目标 (Goal)

从纯手动工作流转向受控的事件驱动提案。

### Step 5.1: 添加事件日志 (Add Event Log)

任务 (Tasks):

```text
1. 添加 logs/events.jsonl。
2. 添加 event.schema.json。
3. 记录 source.created、candidate.created、wiki.page.updated、query.answered、session.ended、review_after.expired。
```

验收标准 (Acceptance criteria):

```text
自动化操作是可审计的。
```

### Step 5.2: 添加会话结晶 (Add Session Crystallization)

任务 (Tasks):

```text
1. 添加 prompts/crystallize-session.md。
2. 将会话中有用的结论转化为候选内容，而不是直接更新 wiki。
3. 需要来源引用或标记为 manual/query/session 来源。
```

验收标准 (Acceptance criteria):

```text
一次有用的讨论可以成为候选内容，而无需绕过审查。
```

### Step 5.3: 添加自动化 PR 提案 (Add Automated PR Proposal)

任务 (Tasks):

```text
1. 允许脚本或代理准备 PR 就绪的补丁集。
2. 需要通过所有检查。
3. 需要所有者审查。
4. 不要自动合并。
```

验收标准 (Acceptance criteria):

```text
自动化减少了文书工作，但不会消除人类判断。
```

## Phase 6: 平台接口 (Platform Interface)

### 目标 (Goal)

在仓库工作流稳定后安全地暴露知识库。

潜在的接口 (Potential interfaces):

```text
只读 MCP 服务器
内部搜索 API
静态文档站点
OKF 包浏览器
所有者/审阅仪表盘
```

验收标准 (Acceptance criteria):

```text
外部接口不会成为权威层。
所有答案仍然可追溯到 wiki 页面和 source refs。
权限边界得到执行。
```

## 最终实施规则 (Final Implementation Rule)

每个阶段必须使系统保持可工作状态。如果前一阶段无法通过检查并产出有用的经过审阅的知识，则不要启动下一阶段。
