# New Design Principles（新设计原则）

> 目的：定义团队 LLM Wiki 的下一代设计纲领。
> 本文档在概念上取代早期的阶段草案，但其本身并不修改现有 repo 的行为。

## 1. Design Thesis（设计纲领）

团队 LLM Wiki 不应被设计为聊天机器人的记忆转储、纯 RAG 索引或文档站点。它应被设计为一种受治理的知识代码库（governed knowledge codebase）。

核心纲领：

```text
Git 是权威层（authority layer）。
Markdown 是人类可读的知识介质。
YAML frontmatter 是机器可读的控制平面。
原始来源（Raw sources）是不可变的证据。
候选（Candidates）是 AI/人类的提案缓冲区。
正式 wiki 页面是经过评审的团队知识。
衍生的索引、搜索语料库、图侧车（graph sidecars）、OKF 导出和可视化是可重建的投影（rebuildable projections）。
```

LLM 应被用作编译器、维护者、评审者和查询助手。它们不应被允许静默地重写团队真相。

## 2. Goals（目标）

重新设计的系统应支持：

1. 存储为版本化 markdown 的持久化团队知识。
2. 有证据支持的正式 wiki 页面。
3. 在正式化之前由人类负责人评审。
4. AI 辅助的摄取、编译、查询、lint 和重构工作流。
5. 基于员工 ID 的责任追踪。
6. 评审生命周期、过期检测、取代（supersession）和置信度管理。
7. 高风险知识的声明级溯源（claim-level provenance）。
8. 可解释的相关页面发现。
9. 生成的索引和评审队列。
10. 可从规范 markdown 重建的搜索和图侧车。
11. 不削弱内部治理的 OKF 兼容导出。
12. 为未来自动化做准备的事件日志。
13. 明确将演示材料排除在正式知识检查之外。

## 3. Non-Goals（非目标）

重新设计的系统不应：

1. 成为纯粹的向量数据库或 RAG 产品。
2. 让 LLM 在未经 PR 评审的情况下合并正式知识。
3. 将 Confluence 镜像快照视为正式真相。
4. 将个人笔记视为团队真相。
5. 在早期阶段依赖图数据库。
6. 在 repo 工作流稳定之前要求 MCP/API 平台。
7. 在内部对每个治理字段都要求 OKF。
8. 自动删除旧知识作为遗忘的一种形式。
9. 将演示资产作为正式知识扫描。
10. 在无策略的情况下将敏感或受限材料放入默认搜索。

## 4. Core Principles（核心原则）

### 4.1 Repo First, Platform Later（Repo 优先，平台在后）

仓库是真相的来源。平台、查看器、搜索服务、图查看器、MCP 网关和 OKF 包都是衍生视图。

如果某个衍生制品被删除，它应能从 repo 内容重建。

### 4.2 Evidence Before Synthesis（证据先于综合）

每个正式 wiki 页面必须有源证据支持。对于低风险的概述页面，页面级 `source_refs` 可能就足够了。对于高风险的操作指南，需要声明级证据。

高风险领域：

```text
runbook 步骤
事件根因
安全和隐私规则
生产架构声明
API 契约
所有权和升级路径
ADR 决策
迁移规则
```

### 4.3 Candidate Buffer Before Formal Knowledge（先有候选缓冲区，再有正式知识）

AI 生成或查询衍生知识必须首先进入 `inbox/candidates/`。正式 wiki 页面只能通过 PR 评审更改。

这创建了一个安全的缓冲区，AI 可以在其中发挥作用而不破坏正式 wiki。

### 4.4 Lifecycle Is Part Of Knowledge（生命周期是知识的一部分）

知识页面不仅仅是内容。它拥有生命周期元数据：

```text
status（状态）
review_state（评审状态）
confidence（置信度）
verified_at（验证时间）
review_after（下次评审时间）
supersedes（取代）
superseded_by（被取代）
memory_policy（记忆策略）
```

知识可以是活跃的、过期的、有争议的、被取代的、已归档的或草稿。查询代理必须将这些状态视为硬性指导。

### 4.5 Page-Level Confidence Is Not Enough Forever（页面级置信度永远不够）

页面级置信度在阶段 0 是可以接受的。为了扩展，高风险声明需要声明级置信度和来源锚点。

使用渐进式模型：

```text
Phase 0: 页面级置信度
Phase 0.5: 高风险事实的声明引用
Phase 1+: 正式操作知识的声明级置信度
```

### 4.6 Explainable Graph Before Smart Graph（先有可解释图，再有智能图）

从确定性的、可解释的图边开始：

```text
frontmatter 相关
标准 markdown 链接
反向链接
共享的 source_refs
所有者和维护者
supersedes / superseded_by
```

LLM 推断的边必须是候选，而不是直接的图事实。

### 4.7 Search Must Be Evaluated（搜索必须经过评估）

搜索不应仅仅因为技术简单就被添加。它必须有一个评估集和已知的失败模式。

最低搜索成功标准：

```text
top-5 预期页面命中率
过期/被取代页面误用率
引用正确性
未知正确性
权限泄露检查
```

### 4.8 Internal Strictness, External Compatibility（内部严格，外部兼容）

内部 wiki 模式应当严格，因为团队知识需要治理。

OKF 导出应当宽松且兼容，因为外部消费者需要可移植性。

因此：

```text
内部模式 != OKF 模式
内部模式 -> OKF 导出配置
```

### 4.9 Human Ownership Is Not Optional（人类所有权不可省略）

每个正式页面需要一个负责人。负责人评审是知识成为团队真相的方式。

AI 可以建议负责人，但不能确认负责人。

### 4.10 Automation Must Produce Reviewable Artifacts（自动化必须产生可评审的制品）

早期自动化应创建：

```text
候选文件
评审队列项
PR
生成的索引
生成的图侧车
报告
```

它不应直接合并或静默更新正式知识。

## 5. Design Slogan（设计口号）

```text
不要构建一个更大的检索系统。
构建一个能够经受检索、评审、修订和时间考验的知识系统。
```

## 6. New Architecture Layers（新架构层次）

```text
Layer 0: 源证据（Source Evidence）
  raw/, confluence-mirror/, 外部引用

Layer 1: 提案与评审（Proposal And Review）
  inbox/candidates/, inbox/reviews/

Layer 2: 正式团队知识（Formal Team Knowledge）
  wiki/

Layer 3: 控制平面（Control Plane）
  AGENTS.md, schemas/, templates/, prompts/, scripts/

Layer 4: 衍生投影（Derived Projections）
  indexes/, graph/, 搜索语料库, OKF 导出, logs/

Layer 5: 未来访问接口（Future Access Interfaces）
  静态查看器, MCP 网关, API, 搜索服务
```

## 7. What Changes From The Current Design（与当前设计相比的变化）

重新设计的系统保留当前的目录理念，但改变了操作侧重点：

| 当前侧重点 | 新侧重点 |
| --- | --- |
| 规则文档化 | 规则强制执行 |
| 页面级源引用 | 源引用加声明引用 |
| 手动索引 | 生成并检查的索引 |
| 阶段计划作为文档 | 阶段计划作为实现门禁 |
| 图作为未来构想 | 生命周期硬化后的确定性图侧车 |
| 搜索作为功能 | 搜索作为评估后的投影 |
| OKF 作为灵感 | OKF 作为导出/导入兼容层 |
| 自动化作为未来代理行为 | 自动化作为显式事件契约和 PR 生产者 |

## 8. First Principle For Implementation（实现的第一性原理）

当在使系统更智能和使系统更可信之间做选择时，优先选择信任。

正确的顺序是：

```text
正确性（correctness） -> 溯源（provenance） -> 生命周期（lifecycle） -> 搜索（search） -> 图（graph） -> 自动化（automation） -> 平台（platform）
```
