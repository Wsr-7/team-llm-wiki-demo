# 旧设计 vs 新设计对比 (Old Design Vs New Design Comparison)

> 目的：将原始仓库设计/阶段草稿与 `docs/llm-wiki-architecture-v2/redesign/` 下的重新设计架构进行对比。
>
> 范围：系统架构、仓库结构、schema 模型、阶段计划、搜索、图谱（graph）、OKF、生命周期（lifecycle）、治理（governance）、自动化和风险控制。

## 1. 执行摘要 (Executive Summary)

旧设计是一个强大的 Phase 0 / MVP 设计，适用于基于 Git 的团队 LLM Wiki。它验证了核心思路：

```text
原始来源证据 -> AI/人工候选 -> 已审查的 wiki 页面 -> 查询/检查工作流
```

新设计并未否定这一基础。它通过添加更强的边界、生命周期规则、出处（provenance）、生成产物、质量门禁（quality gates）以及阶段级验收标准，将其强化为一个长期运行的知识系统。

简而言之：

```text
旧设计：证明 LLM Wiki 工作流能够运行。
新设计：使 LLM Wiki 足够可信赖以长期持续运行。
```

## 2. 高层定位 (High-Level Positioning)

| 维度 | 旧设计 | 新设计 |
| --- | --- | --- |
| 主要身份 | 基于 GitHub 仓库的团队 LLM Wiki | 受治理的知识代码库 |
| 主要目标 | 演示 raw -> candidate -> wiki 工作流 | 构建可信、可审计、可演进的知识基础设施 |
| 主要设计单元 | Markdown 页面和提示词工作流 | 具有生命周期、出处、策略和衍生投影（projection）的知识对象 |
| 主要优势 | 轻量、易理解、良好的演示骨架 | 更强的生产方向、更清晰的门禁、更好的长期健康性 |
| 主要劣势 | 许多规则有文档但未强制执行 | 更复杂，需要严格按阶段实施 |
| Agent 角色 | 在提示词协议下进行摄取、编译、查询、检查 | 提案引擎、验证助手、搜索助手、图谱/搜索/导出生成器，但永远不是沉默的权威 |
| 真相来源 | Git 仓库中的 `wiki/` | Git 仓库中的 `wiki/` 及来源证据和治理元数据 |
| 衍生产物 | 未来的图谱和索引 | 显式生成的索引、搜索语料库、图谱 sidecar、OKF 导出、事件日志 |

## 3. 系统架构对比 (System Architecture Comparison)

### 3.1 旧架构 (Old Architecture)

旧系统围绕核心 LLM Wiki 流水线展开：

```text
来源
  -> raw/
  -> inbox/candidates/
  -> wiki/
  -> indexes/
  -> 后续 graph/search/automation
```

其主要架构边界为：

```text
raw/                 不可变的来源证据
inbox/candidates/    提议的知识
wiki/                正式的已审查知识
personal/            个人知识和个人资料空间
confluence-mirror/   外部快照，非正式真相
indexes/             导航和审查队列
graph/               未来的图谱 sidecar
logs/                操作日志
```

这在方向上是正确的。主要差距在于旧架构没有完全分离规范内容、提议内容、衍生内容、未来接口和展示材料。

### 3.2 新架构 (New Architecture)

新架构使用显式的分层：

```text
第 0 层：来源证据 (Source Evidence)
  raw/, confluence-mirror/, external references

第 1 层：提议与审查 (Proposal And Review)
  inbox/candidates/, inbox/reviews/

第 2 层：正式团队知识 (Formal Team Knowledge)
  wiki/, personal/*/profile.md

第 3 层：控制面 (Control Plane)
  AGENTS.md, schemas/, templates/, prompts/, scripts/, GitHub workflows

第 4 层：衍生投影 (Derived Projections)
  indexes/, graph/, search corpus, OKF export, logs/

第 5 层：未来访问接口 (Future Access Interfaces)
  static viewer, MCP gateway, API, search service
```

### 3.3 主要架构差异 (Main Architecture Difference)

| 主题 | 旧设计 | 新设计 |
| --- | --- | --- |
| 规范内容 vs 衍生内容 | 隐含 | 显式 |
| AI 写入边界 | 主要由提示词定义 | 显式：AI 可以写入候选/审查/衍生产物，不能静默合并正式 wiki |
| 运行时接口边界 | 未来想法 | 在仓库工作流成熟后单独分层 |
| 展示材料 | 未明确排除 | `html-ppt*` 明确视为展示/说服材料，排除在正式 lint/搜索/图谱之外 |
| 图谱/搜索权威 | 未来功能 | 仅限衍生投影；规范 markdown/frontmatter 仍是权威 |
| 自动化权威 | 未来能力 | 自动化创建可审查的产物，而非静默的真相 |

## 4. 仓库结构对比 (Repository Structure Comparison)

### 4.1 旧目录结构 (Old Directory Structure)

旧仓库已有良好的骨架：

```text
raw/
confluence-mirror/
personal/
inbox/
wiki/
schemas/
templates/
prompts/
scripts/
indexes/
graph/
logs/
docs/
design-draft/
```

旧结构优势：

```text
1. 清晰的 raw/candidate/wiki 分层。
2. 个人空间与团队真相分离。
3. Confluence 镜像未混入正式 wiki。
4. 通过 AGENTS.md + schemas + templates + prompts 实现 Schema Pack。
5. 预留了后续的 graph/index/log 目录。
```

旧结构劣势：

```text
1. design-draft 和 html-ppt 相关材料未明确排除在正式检查之外。
2. inbox/reviews 未按过时(stale)、矛盾(contradictions)、缺少负责人(missing owner)、低置信度(low confidence)、敏感内容(sensitive content)进行分类。
3. graph/ 基本是占位符。
4. indexes/ 没有搜索语料库或分块清单(chunk manifest)。
5. 没有 okf/ 导出区域。
6. logs/ 缺少查询、脱敏和事件日志。
7. scripts/ 有基本检查，但没有生命周期/搜索/图谱/导出生成器。
```

### 4.2 新目录结构 (New Directory Structure)

新设计保留了旧的骨架，但将其扩展为可操作的分区：

```text
index.md                         # 生成的 OKF 兼容根索引，后期阶段
log.md                           # 生成的 OKF 兼容根日志，后期阶段
.github/workflows/               # CI 检查
raw/                             # 不可变的来源证据
confluence-mirror/               # 单向快照
personal/                        # 个人资料和非正式的个人知识
inbox/candidates/                # 提议的知识
inbox/reviews/stale/             # 过时页面的审查队列
inbox/reviews/contradictions/    # 矛盾审查记录
inbox/reviews/missing-owner/     # 所有权问题
inbox/reviews/low-confidence/    # 置信度问题
inbox/reviews/sensitive-content/ # 隐私和敏感性问题
wiki/                            # 正式的已审查知识
schemas/                         # 机器可读和人类可读的契约
templates/                       # 页面和审查模板
prompts/                         # agent 任务协议
scripts/                         # 验证器和生成器
indexes/INDEX.md                 # 生成的导航
indexes/REVIEW_QUEUE.md          # 生成的审查队列
indexes/QUERY_EVAL.md            # 搜索评估集
indexes/search/corpus.jsonl      # 生成的搜索语料库
indexes/search/chunks.jsonl      # 生成的分块
graph/nodes.jsonl                # 生成的图谱节点
graph/edges.jsonl                # 生成的图谱边
graph/backlinks.jsonl            # 生成的反向链接
graph/graph-report.md            # 生成的图谱健康报告
graph/viz.html                   # 静态图谱查看器
okf/                             # 生成的 OKF 兼容包
logs/query.md                    # 查询审计
logs/redaction.md                # 脱敏审计
logs/events.jsonl                # 自动化和生命周期事件
docs/llm-wiki-architecture-v2/   # 架构审查和重新设计文档
```

### 4.3 主要目录差异 (Main Directory Difference)

| 目录区域 | 旧设计 | 新设计 |
| --- | --- | --- |
| `raw/` | 带有清单/来源的来源文件夹 | 相同，但增加了严格的哈希和不可变性检查 |
| `inbox/reviews/` | 通用审查区域 | 分类的审查队列：过时、矛盾、负责人、置信度、敏感内容 |
| `indexes/` | 手动导航和审查队列 | 生成的导航、审查队列、查询评估、搜索语料库、分块 |
| `graph/` | 未来的 sidecar 占位符 | 生成的节点/边/反向链接/报告/静态查看器 |
| `okf/` | 不存在 | 生成的互操作性导出 |
| `logs/` | 操作日志 | 操作、摄取、lint、查询、脱敏、事件日志 |
| `design-draft/html-ppt*` | 在检查中模糊不清 | 明确排除为展示材料 |
| `scripts/` | 基本检查脚本 | 验证器以及索引、审查队列、搜索、图谱、OKF 的生成器 |

## 5. Schema 模型对比 (Schema Model Comparison)

### 5.1 旧页面 Schema (Old Page Schema)

旧页面 schema 是页面级别且具有治理意识的：

```yaml
id: kb:<type>:<slug>
title: <title>
type: overview | glossary | concept | team | project | system | practice | runbook | decision | learning | mirrored
status: draft | candidate | active | stale | superseded | archived
review_state: unreviewed | reviewed | needs-review | disputed
confidence: 0.00
visibility: internal | restricted | confidential
owners:
  - staff:12345678
source_refs:
  - raw:<category>:<source-id>
related: []
created_at: YYYY-MM-DD
updated_at: YYYY-MM-DD
```

这是一个良好的起点。它可以治理页面，但无法完全治理高风险声明、搜索行为、记忆生命周期、导出策略或自动化事件。

### 5.2 新页面 Schema (New Page Schema)

新 schema 保留了旧字段，并增加了生命周期、记忆、索引和出处的扩展：

```yaml
production_applicable: true
memory_tier: semantic | procedural | episode | raw_observation
memory_policy:
  retention_class: durable | normal | transient
  decay_half_life_days: 180
index_policy:
  include_in_default_search: true
  allowed_roles: []
  redaction_required: false
claim_refs: []
```

### 5.3 声明引用差异 (Claim Reference Difference)

旧设计：

```yaml
source_refs:
  - raw:runbooks:2026-06-01-demo-payment-runbook
```

新设计：

```yaml
claim_refs:
  - claim_id: claim:payment:failover-requires-degradation-confirmation
    statement: "Failover requires degradation confirmation before switching providers."
    confidence: 0.78
    source_refs:
      - source_ref: raw:runbooks:2026-06-01-demo-payment-runbook
        source_path: raw/runbooks/2026-06-01-demo-payment-runbook/source.md
        start_line: 1
        end_line: 3
        quote_hash: sha256:<hash>
    last_confirmed_at: 2026-06-01
    contradiction_refs: []
```

主要差异：

```text
旧设计：页面知道它来自哪个来源。
新设计：高风险声明知道确切支持它的来源范围。
```

### 5.4 候选 Schema 差异 (Candidate Schema Difference)

旧候选：

```yaml
candidate_origin: raw | personal | mirror | query | manual
candidate_intent: ingest | compile | promotion | sync
candidate_status: proposed | in_review | promoted | rejected | superseded
```

新候选：

```yaml
candidate_origin: raw | personal | mirror | query | manual | session
candidate_intent: ingest | compile | promotion | sync | crystallize
candidate_status: proposed | in_review | promoted | rejected | superseded
quality:
  structure_score: 0.00
  citation_score: 0.00
  consistency_score: 0.00
  actionability_score: 0.00
  owner_clarity_score: 0.00
  overall: 0.00
quality_status: pass | needs-rewrite | needs-human-review
```

主要差异：

```text
旧设计：候选是一个 AI/人工提议缓冲区。
新设计：候选是一个被评分、可审查、可提升的知识提案。
```

### 5.5 来源清单差异 (Source Manifest Difference)

旧设计有来源清单，但演示用的哈希不是真正的 SHA256 哈希。

新设计要求：

```yaml
id: raw:<category>:<yyyy-mm-dd-slug>
title: <title>
source_type: doc | runbook | incident | meeting | code-chunk | external | confluence
collector: staff:12345678
collected_at: YYYY-MM-DD
sensitivity: internal | restricted | confidential
hash: sha256:<real-source-md-hash>
status: captured | superseded | rejected
origin:
  system: manual | confluence | github | slack | meeting | external
  url: ""
```

主要差异：

```text
旧设计：来源清单存在。
新设计：来源清单成为可验证的证据契约。
```

## 6. 阶段计划对比 (Phase Plan Comparison)

## 6.1 旧阶段计划 (Old Phase Plan)

旧计划大致为：

| 阶段 | 旧关注点 |
| --- | --- |
| Phase 0 | 启动和基线仓库骨架 |
| Phase 1 | 手动循环和最小可用知识库 |
| Phase 2 | 质量门禁和 PR 检查 |
| Phase 3 | 搜索和 QA 增强 |
| Phase 4 | 图谱和生命周期治理 |
| Phase 5 | 自动化和企业集成 |

旧阶段顺序是合理的，但一些信任关键项出现得太晚。例如，生命周期、替代（supersession）、来源哈希、审查队列和声明级出处是基础性的，但它们大多被视为后期的治理能力。

## 6.2 新阶段计划 (New Phase Plan)

新计划为：

| 阶段 | 新关注点 | 关键成果 |
| --- | --- | --- |
| Phase 0 | 基线加固 (Baseline Hardening) | 现有骨架变为可检查且 CI 强制执行的 |
| Phase 0.5 | 生命周期与出处 (Lifecycle And Provenance) | 来源哈希、审查队列、置信度规则、声明引用 |
| Phase 1 | 最小可用团队 Wiki (Minimum Usable Team Wiki) | 真实的 source -> candidate -> formal page 工作流 |
| Phase 2 | 搜索与查询评估 (Search And Query Evaluation) | 搜索语料库、分块、查询评估、安全查询工作流 |
| Phase 3 | 图谱与影响导航 (Graph And Impact Navigation) | 确定性图谱 sidecar 和相关/影响查询 |
| Phase 4 | OKF 互操作性 (OKF Interoperability) | 生成的 OKF 兼容包 |
| Phase 5 | 自动化与结晶化 (Automation And Crystallization) | 事件日志、会话结晶化、PR 提案 |
| Phase 6 | 平台接口 (Platform Interface) | 只读 MCP/API、仪表板、静态查看器、搜索 API |

### 6.3 主要阶段差异 (Main Phase Difference)

| 主题 | 旧计划 | 新计划 |
| --- | --- | --- |
| 质量门禁 | Phase 2 | Phase 0 和 Phase 0.5 |
| 生命周期 | 主要为 Phase 4 | Phase 0.5 |
| 来源哈希 | 未充分强调 | Phase 0 |
| 声明级出处 | 不显式 | Phase 0.5 |
| 搜索 | Phase 3 | Phase 2，但仅在查询评估存在之后 |
| 图谱 | Phase 4 | Phase 3，在生命周期和搜索基础之后 |
| OKF | 非正式阶段 | Phase 4 |
| 自动化 | Phase 5 企业集成 | Phase 5 事件驱动、仅 PR 的自动化 |
| 平台/MCP | 混入后期集成 | 单独的 Phase 6，在仓库工作流成熟之后 |

核心转变：

```text
旧计划：目录 -> 工作流 -> PR 检查 -> 搜索 -> 图谱 -> 自动化。
新计划：信任 -> 出处 -> 生命周期 -> 真实工作流 -> 经评估的搜索 -> 图谱 -> 互操作性 -> 自动化 -> 平台。
```

## 7. 逐阶段详细对比 (Phase-By-Phase Detailed Comparison)

### 7.1 Phase 0

| 方面 | 旧 Phase 0 | 新 Phase 0 |
| --- | --- | --- |
| 目标 | 创建基线骨架和演示 | 加固现有骨架 |
| 主要工作 | 目录、README、AGENTS、schema、模板、提示词、演示页面 | 正式路径范围、真实 YAML 解析器、JSON Schema 验证、来源哈希、CI、CODEOWNERS、分支保护、演示语义 |
| 成功标志 | 仓库看起来像一个 LLM Wiki | 仓库能够可靠地自我检查 |
| 关键风险 | 演示骨架有未强制执行的规则 | 范围/检查/来源完整性变为可强制执行 |

新 Phase 0 任务：

```text
1. 定义正式检查范围。
2. 将 design-draft/html-ppt 材料排除在正式检查之外。
3. 替换自定义 YAML 解析器。
4. 添加 JSON Schema 验证。
5. 添加 check-source-manifests。
6. 修复演示页面状态语义。
7. 添加 CI 工作流。
8. 替换占位符 CODEOWNERS。
9. 更新分支保护说明。
```

### 7.2 Phase 0.5

旧设计没有显式的 Phase 0.5。

新 Phase 0.5 在知识库增长之前引入生命周期和出处：

```text
1. build-index.ts / check-index.ts
2. build-review-queue.ts
3. check-review-after.ts
4. check-confidence-rules.ts
5. check-superseded-references.ts
6. claim-ref schema 和最小示例
7. 矛盾审查模板和提示词
```

为什么这很重要：

```text
如果生命周期和出处只在 wiki 增长后才引入，仓库中已经会包含过时、薄弱或无法追溯的知识。
```

### 7.3 Phase 1

| 方面 | 旧 Phase 1 | 新 Phase 1 |
| --- | --- | --- |
| 目标 | 手动循环和最小可用知识库 | 真实的团队使用，带有负责人审查的正式页面 |
| 来源输入 | 演示或初始来源 | 3-5 个真实安全的内部来源 |
| 候选流 | 手动摄取和编译 | 摄取、编译、质量说明、开放问题 |
| 正式化 | PR 就绪的 wiki 补丁 | 负责人审查的 PR，附带生成的索引/审查队列 |
| 查询试验 | 基本查询提示词 | 10 个真实问题，带有 unknown/candidate 反馈循环 |

主要差异：

```text
旧 Phase 1 证明工作流机制。
新 Phase 1 证明工作流在真实知识上的有用性。
```

### 7.4 Phase 2

| 方面 | 旧 Phase 2 | 新 Phase 2 |
| --- | --- | --- |
| 目标 | 质量门禁和 PR 检查 | 搜索和查询评估 |
| 变更原因 | 质量门禁太晚了 | 质量门禁移至 Phase 0/0.5 |
| 主要产物 | CI、PR 检查 | QUERY_EVAL.md、corpus.jsonl、chunks.jsonl、search.ts、evaluate-search.ts |
| 搜索理念 | 改进检索 | 在向量/混合搜索之前评估检索安全性 |

新 Phase 2 不会立即开始向量搜索。它从评估开始：

```text
1. 定义代表性问题。
2. 定义期望的页面命中结果和禁止使用的页面。
3. 生成语料库和分块。
4. 构建词法/rg 回退搜索。
5. 测量 hit@5 和过时内容误用。
6. 仅在基线存在后添加混合搜索。
```

### 7.5 Phase 3

| 方面 | 旧 Phase 3 | 新 Phase 3 |
| --- | --- | --- |
| 目标 | 搜索和 QA 增强 | 图谱和影响导航 |
| 变更原因 | 搜索移至 Phase 2 | 图谱现在有自己的专注阶段 |
| 主要产物 | QMD/vector/rerank/search | nodes.jsonl、edges.jsonl、backlinks.jsonl、graph-report.md、viz.html |
| 边策略 | 存在相关规则 | 每条边都需要理由和证据 |

新图谱原则：

```text
Markdown/frontmatter 是规范的。
图谱 sidecar 是衍生的。
LLM 推断的边必须成为候选，而不是直接的图谱事实。
```

### 7.6 Phase 4

| 方面 | 旧 Phase 4 | 新 Phase 4 |
| --- | --- | --- |
| 目标 | 图谱和生命周期治理 | OKF 互操作性 |
| 变更原因 | 生命周期提前，图谱移至 Phase 3 | 外部可移植性成为一个独立阶段 |
| 主要产物 | 图谱/生命周期脚本 | okf/、export-okf.ts、okf index.md、okf log.md、跨团队元数据 |

新 OKF 原则：

```text
内部 schema 保持严格。
OKF 导出是生成的兼容性视图。
不要为了外部兼容性而削弱内部治理。
```

### 7.7 Phase 5

| 方面 | 旧 Phase 5 | 新 Phase 5 |
| --- | --- | --- |
| 目标 | 自动化和企业集成 | 带审计的自动化和结晶化 |
| 自动化模型 | 广泛的未来集成 | 先做事件日志，仅 PR 提案 |
| 关键产物 | MCP/API/集成 | logs/events.jsonl、crystallize-session 提示词、自动化的 PR 提案 |
| 安全立场 | 未完全分离 | 显式禁止自动合并，禁止静默正式更新 |

新自动化规则：

```text
自动化可以创建候选、审查项、报告、生成产物和 PR。
自动化不得静默合并正式的 wiki 变更。
```

### 7.8 Phase 6

旧设计没有明确分离出平台阶段。

新 Phase 6 仅在治理稳定后引入平台接口：

```text
只读 MCP 服务器
内部搜索 API
静态文档站点
OKF 包浏览器
负责人/审查仪表板
```

主要原则：

```text
外部接口是仓库的消费者，而非权威层。
```

## 8. 搜索设计对比 (Search Design Comparison)

| 方面 | 旧搜索设计 | 新搜索设计 |
| --- | --- | --- |
| 主要思路 | 以后使用 QMD/BM25/vector/rerank | 从语料库、分块、查询评估、词法基线开始 |
| 评估 | 提到但不是核心 | 在混合搜索之前必须进行 |

| 分块清单 | 不显式 | `indexes/search/chunks.jsonl` |

## 9. 图谱设计对比 (Graph Design Comparison)

| 方面 | 旧图谱设计 | 新图谱设计 |
| --- | --- | --- |
| 状态 | 后期阶段设计 | 专门的衍生投影阶段 |
| 规范来源 | 隐含的 markdown/frontmatter | 显式的 markdown/frontmatter 权威 |
| 边生成 | 相关链接、反向链接、共享来源引用、显式相关 | 相同，但每条边必须有理由和证据 |
| LLM 推断的边 | 并非总是明确约束 | 必须首先进入 candidate/review |
| 输出 | nodes/edges/backlinks | nodes/edges/backlinks + graph-report + 静态可视化 |
| 目的 | 关系和相关发现 | 影响导航、图谱健康、相关发现、静态检查 |

新边示例：

```json
{"from":"kb:runbook:payment-failover","to":"kb:system:payment-gateway","type":"runbook_for","reason":"explicit-frontmatter","evidence":["wiki/runbooks/payment/payment-failover.md"]}
```

主要差异：

```text
旧设计计划了一个图谱。
新设计将图谱视为可解释、可重建、可审计的投影。
```

## 14. 展示材料处理 (Presentation Material Handling)

用户已澄清 `html-ppt-assets/` 和 `html-slide-design-scheme/` 是用于向团队成员解释和推广 LLM Wiki 理念的展示尝试。

新设计明确将其视为：

```text
展示材料
沟通宣传品
非正式 wiki 内容
非图谱输入
非搜索语料库输入
非来源引用检查的内容
非员工 ID 检查的内容
非断链检查的内容
```

建议排除的路径：

```text
design-draft/html-ppt-assets/
design-draft/html-slide-design-scheme/
```

建议更广泛的注意事项：

```text
除非有意识地创建了专门的设计文档检查，否则 design-draft/ 不应被正式 wiki 检查扫描。
```

## 15. 十个最重要的变化 (Ten Most Important Changes)

1. 新设计增加了 Phase 0.5 用于生命周期和出处加固。
2. 新设计明确将 `html-ppt*` 展示资产排除在正式知识处理之外。
3. 新设计要求使用真实的 SHA256 来源哈希替代占位符来源哈希。
4. 新设计从页面级 `source_refs` 升级到高风险声明级 `claim_refs`。
5. 新设计将 `INDEX.md` 从手动导航改为可生成和可检查的导航。
6. 新设计将置信度规则转化为脚本和审查队列项。
7. 新设计要求在向量或混合搜索之前进行查询评估。
8. 新设计使图谱 sidecar 具有确定性、可解释性和可重建性。
9. 新设计添加了 OKF 导出配置，而不是强制内部 schema 变成 OKF。
10. 新设计使自动化成为事件驱动、可审计且仅限 PR 的。

## 16. 不应改变的内容 (What Should Not Change)

旧设计有几个正确的基础应予以保留：

```text
1. Git 仓库仍然是权威层。
2. 正式团队知识仍位于 wiki/ 下。
3. raw/ 仍然是来源证据。
4. inbox/candidates/ 仍然是 AI/人工提议缓冲区。
5. personal/ 在提升前仍是非正式的。
6. confluence-mirror/ 仍然是单向快照，而非真相。
7. AGENTS.md + schemas + templates + prompts 仍然是 Schema Pack。
8. staff:######## 仍然是规范的身份模型。
9. AI 不应静默写入正式真相。
10. 相关页面发现应从可解释的信号开始。
```

新设计强化了这些基础，而不是替换它们。

## 18. 最终对比判断 (Final Comparison Judgment)

旧设计适合于解释概念和证明基本工作流。

新设计适合于将概念转化为可维护的团队知识系统。

紧凑总结：

```text
旧设计 = MVP 骨架 + 工作流演示。
新设计 = 治理优先架构 + 生命周期加固 + 经评估的检索 + 衍生图谱/导出/自动化层。
```

下一步实际的工程行动应该是最先只实施 Phase 0 和 Phase 0.5。这将为仓库提供真实的信任保证，而无需过早构建向量搜索、图谱可视化工具、MCP 服务器或自动化平台。
